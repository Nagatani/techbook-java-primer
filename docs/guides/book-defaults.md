# 本書の既定の選択

同じ目的に複数の書き方・ライブラリがあるとき、本書がどれを使うかの一覧です（2026-11-24に著者が決めた）。
本文で選択肢を並べたら、ここにある既定を「本書では〜を使います」と言い切り、理由を1文添えます。
サンプル・演習・付録のコードもこの既定にそろえます（2026-11-24にそろえた。付録Eの誤りの例と、付録B.05・B.08の違いの説明は除く）。
既定と違う書き方を載せるときは、その理由（古いコードを読むため、など）を書きます。

| 問い | 本書の既定 | 理由（本文に書く要点） | 書いた場所 |
|---|---|---|---|
| ビルドツール | Maven | 設定がXMLにそのまま書かれていて読める | 第22章 |
| JSONライブラリ | Gson | 依存が1つで、設定を書かずにすぐ使える。JacksonはSpringなどの開発で出会うので、第22章で書き方の違いだけを見る | 第16章・第22章 |
| データベース | H2 | JARを1つ加えるだけで動く。SQLiteは統合プロジェクトの初版（第25・26章の事例）にだけ残す。H2の次に1つだけ触るならPostgreSQL（無料で、SQLの標準に近く、本番でも広く使われている） | 第24章 |
| 独自の例外 | 利用者に伝えて対処できる誤りは検査例外、コードを直すべき誤りは非検査例外 | 対処を忘れるとコンパイラーが教えてくれる。非検査例外に寄せる流儀もある旨を添える | 第13章・第25章 |
| Streamの結果をリストにする | `toList()` | Java 25が対象。変更できるリストが要るときとJava 15以前のコードでは`collect(Collectors.toList())`（第12章の脚注）。統合プロジェクトの初版のコードはそのまま | 第12章 |
| Swingのウィンドウ | `JFrame`を継承せず、オブジェクトとして持つ | JFrameの多数のメソッドを自分のクラスに引き継がない。第25章の「迷ったら、まず合成」 | 第17章・第18章 |
| リスト | `ArrayList` | | 第9章 |
| switch | アロー形式（`->`） | | 第2章 |
| `var` | ほとんど使わない | | 第10章 |
| ログ | `java.util.logging`。課題では最初は`IO.println`でよく、提出前にデバッグ用の出力を消して回るようになったら切り替える | 依存を増やさない。重要度を付ければ消さずに出す量だけを変えられる | 第13章・第26章 |
| 小さなテキストファイルの読み書き | `Files.readAllLines`・`Files.writeString`。1行ずつ処理するときや大きなファイルは`Files.newBufferedReader` | 課題の規模なら全体を読むほうが短く書ける | 第14章 |
| データを保存する形式 | CSVかJSON（Gson）。直列化は使わない | クラスを変えると読めなくなる。信頼できないデータの非直列化は危険。直列化は既存のコードを読むために知る（付録I） | 第14章 |
| for文とStream | 短い処理はどちらでもよい。途中で抜ける・検査例外・添え字・外の変数の書き換えはfor文 | 入れ子で読みにくくなったらStreamに書き換える | 第12章 |
| ジェネリクス | まず標準ライブラリの型を読んで使えること。自作は型ごとに書き分けそうになったとき | | 第10章 |
| EDTの外で動かす処理 | 結果を表示するだけなら`Thread`と`invokeLater`、進捗の表示や中断が要るなら`SwingWorker` | | 第19章 |
| Javadoc | `public`なクラスとメソッドに、何をするかの1文と`@param`・`@return`・`@throws` | メソッド名の言い換えではなく、値の範囲や`null`の扱いなど使う側が知りたいことを書く | 第22章 |
| CSVの読み方 | 自分のプログラムが書き出し、値にカンマや改行を含めないと決めたCSVは`split(",")`、Excelやほかのシステムが作ったCSVはライブラリ（Apache Commons CSV） | 他人の作ったCSVには引用符やBOMが入りうる | 第14章・第26章 |
| 共有データの守り方 | 迷ったら`synchronized`。変数1つを増やすだけなら`AtomicInteger` | 調べてから書き換えるような複数の操作をまとめて守れる | 第15章 |
| `CompletableFuture` | `supplyAsync`・`thenApply`・`join`の3つを覚え、残りは必要になったら一覧から探す | | 第15章 |
| 仮想スレッド | 並行処理はスレッドプールから学ぶ。ネットワークの応答を待つようなタスクを多数扱う新しいプログラムは仮想スレッド | 仮想スレッドもスレッドプールの考え方の上に作られている | 第15章 |
| HTTPクライアント | `HttpClient` | `HttpURLConnection`は古いコードや記事で出会うので読むために知る。ソケットの例はHTTPがテキストのやり取りだと確かめるため | 第16章 |
| GUIの教材 | Swing。本書を終えて新しく画面を作るなら、複数の人がブラウザーから使えるWebアプリケーション（Spring Bootなど） | JDKだけで動き、イベント駆動やモデルと表示の分け方を追加の部品なしで学べる。考え方はJavaFXやWebでも同じ | 第17章・第26章 |
| 部品の配置 | レイアウトマネージャー。座標で並べる`setLayout(null)`は課題の提出物では使わない | OSや文字の大きさが違うと崩れ、ウィンドウの大きさに追従しない | 第17章 |
| リスナーの書き方 | ラムダ式。中身が3行を超えたらメソッドに分け、ラムダ式からはそれを呼ぶだけにする | | 第18章 |
| ショートカットキー | キーバインディング（`InputMap`・`ActionMap`）。KeyListenerはキーの情報を確かめる例 | KeyListenerはフォーカスのある部品にしかキーが届かない | 第18章・第19章 |
| 入力の検査 | 誤りの確定は送信ボタンを押したとき。フォーカスが外れたときや入力のたびは、欄の色や文字数の表示などの目印だけ | 打ち終わる前からエラーを出すとうるさい | 第18章・第19章 |
| TDD | 必須にしない。入力と答えがはっきりした計算のメソッドで試す | | 第21章 |
| テストカバレッジ | 数字を目標にしない（本文の80%は設定の書き方の例） | テストが通っていない行を見つけるために使う。結果を確かめないテストでも割合は上がる | 第21章 |
| 自作かライブラリか | 課題で学ぶ処理は自作。仕様が文書で決まっていて例外の多い処理（CSV・JSON）とセキュリティにかかわる処理はライブラリか標準API。それ以外で数十行で書けてテストできる処理は自作。課題では課題文で指定されたライブラリだけ | | 第22章・第26章 |
| 配布の方法 | 課題の提出は実行可能JAR、Javaの入っていない友人には`jpackage`の`app-image`、ライブラリを使うもの（統合プロジェクト）はJARと`lib` | | 第23章 |
| JARの作り方 | ふだんは`mvn package`。`jar`コマンドは中身を知るために一度手で打つ | | 第23章 |
| 外部ライブラリを含むJAR | まず`Class-Path`と`lib`。配る相手が多く渡し忘れを避けたいときはFat JAR（付録D） | `lib`を渡し忘れると`NoClassDefFoundError`になる | 第23章 |
| SQLを書く場所 | 表が1つでもDAOに集める | 表の列を変えたときに直す場所が1つで済む。第25章のリポジトリも目的は同じ（脚注） | 第24章 |
| 日時の保存 | 1つのタイムゾーンで使うなら`TIMESTAMP`と`LocalDateTime`。複数のタイムゾーンから使うならUTCにそろえる | | 第24章 |
| 設計判断記録の対象 | 選択肢を2つ以上比べて迷った判断だけ。課題なら2〜3件 | | 第25章 |
| 層の分け方 | 数百行の課題でも画面と計算のクラスは分ける。保存の層はファイルやデータベースに保存するようになってから | 計算をテストできるようになる | 第25章 |
| 作る順番の計画 | 機能ごとに縦に切る | 層のつなぎ目の問題に早く気づけ、チームで分担しやすい | 第25章 |
| バージョン管理 | 統合プロジェクトを始めるときからGit。手順ごとにコミットする | うまくいかなかったときにその手順の前に戻れる | 第26章 |
| 本書のあとに進む方向 | まず自動テストと自動ビルド、次にWebアプリケーション | サービスより下の層をテストで守ったまま画面を替えられる | 第26章 |
| 名前に日本語を使うか | 演習は英語の名前。テストのメソッド名だけは何を確かめるかを日本語で書いてよい | 標準ライブラリの英語の名前と混ざらず、ほかの人も読める | 第2章 |
| 文字列の作り方 | リテラルで作り、`new String()`は書かない。文字列プールは1文で触れるだけ | 理由は`==`の結果でわかる（節「文字列の比較」） | 第2章 |
| 演習の規模でクラスに分けるか | 分ける。1つのクラスでも書ける規模だが、練習のためにあえて分ける | 規模が大きくなったときに使う型を小さいうちに身につける | 第3章 |
| クラスを分ける目安 | 役割を1文で説明して「〜と〜をする」と「と」でつながったら分ける | | 第4章 |
| パッケージの分け方 | 演習なら分けないか、`model`と画面・入出力の2〜3個。6つに分けるのはクラスが数十個になってから。`util`は作らない | `util`は何でも入る箱になりやすい | 第4章 |
| 継承の深さ | 自分で設計するときは親と子の1段まで。2段目が欲しくなったらフィールドに持つ（合成）。第5章の発展課題は3段の階層を確かめるための例外 | | 第5章 |
| `instanceof`とキャスト | 種類で分岐したくなったら、まず親クラスにメソッドを足してオーバーライドする。`instanceof`は`equals`の引数のように自分で変えられない型に使う | 子クラスを足しても`if`を書き足さずに済む | 第5章 |
| `final`を付ける変数 | 作ったあとで変えないフィールドだけ。ローカル変数と引数には付けない | | 第6章 |
| リストの防御的コピー | コンストラクターで`List.copyOf`して持ち、getterはそのまま返す。配列は受け取るときと返すときにコピー | 1回のコピーで中も外も変えられなくなる | 第6章 |
| ビルダー | 引数が4〜5個を超え、省略できるものが多いときだけ。必須の値だけならコンストラクターかRecord。課題で書くのは第6章だけ | | 第6章 |
| `final`クラス | 不変クラスだけ`final`にする。ほかは継承するかを決めてから | | 第6章 |
| ファクトリ | 生成する型を入力や設定で切り替えるときと、生成に検証や組み立てが要るとき。種類が1つで手順も単純なら作らない | | 第7章 |
| シングルトン | 課題では使わない。1つで足りるオブジェクトも`main`で作って引数で渡す | テストで差し替えにくく、状態を隠し持つ | 第8章 |
| データと処理の置き場所 | 基本は第3章のように1つのクラスにまとめる。データの種類が決まっていて処理があとから増えるときだけRecordとswitchに分ける（DOP） | | 第8章 |
| 待ち行列 | `Queue`として`ArrayDeque`。`LinkedList`は知識として知っておけば十分 | | 第9章・第13章 |
| Mapでキーがないとき | `getOrDefault`でキーがないときの値を指定する | `null`の確認を書かずに1行で読める | 第9章 |
| 走査中の削除 | 演習ではIteratorの`remove`。ふだんは`removeIf` | しくみを一度知る | 第9章 |
| 例外のログを書く層 | 例外を最後に受け止める画面に近い層で1回だけ。途中の層は原因を付けて投げ直す。利用者への表示は`IO.println`、調べるための記録は`java.util.logging` | 二重に記録しない | 第13章 |
