# 第22章 ドキュメントと外部ライブラリ 要約

行番号・サンプルコード番号の正確な対応は `docs/book-index/chapter22-documentation-and-libraries.md` を参照する。

## 章の概要

- 前半はJavadoc（コメントの書き方、主要タグ、生成方法）、後半は外部ライブラリの利用（クラスパス、Mavenによる依存関係管理、代表的なライブラリの紹介、選定指針）を扱う
- 紹介するライブラリはGson、Jackson、Apache Commons Lang/IO、OkHttp、Lombok、Guavaの6種で、それぞれpom.xmlの依存関係と使用例・実行結果を示す
- 外部ライブラリとクラスパス、Mavenでの依存関係の書き方を正式に説明する章で、第16章（Jackson）と第21章（JUnit・Mockito）から誘導される
- 前提は第4章（クラス）、第13章（例外処理）、第14章（ファイルI/O）。第21章（ユニットテスト）は推奨扱い
- ビルドツールはMavenだけを扱い、Gradleは名前と年表に出るだけ。「実践的な開発フロー」の後ろに「もう1つのビルドツール：Gradle」（build.gradle/build.gradle.kts、Gsonの依存関係の例22-21、Gradle Wrapper、付録Gへの誘導）を加え、学習目標とまとめも合わせた。Docker（gradle:jdk25、Gradle 9.8）でWrapperの生成とビルドを確かめた（2026-11-12に解消）

## 構成上の問題

- Gradleの扱い
    + 学習目標は「Mavenを例にしたビルドツールの役割と概念」に改めてあり、本文もMavenだけで一貫している
    + 第21章の21-14・21-15はGradle（`./gradlew test`、build.gradle）を使うが、本書でGradleを説明する章はない（第21章は「Mavenを例に第22章で学びます」と断る）。第21章をMavenの例にし、本章にGradleの紹介を加えた（2026-11-12に解消）
- 前提知識の矛盾（推奨知識のビルドツール、第21章との相互参照）は解消した。第21章は推奨から第22章を外し、JUnitの追加手順をIntelliJ IDEAで示して本章へ誘導する（2026-11-11に解消）
- 章内の内容の重複（「トラブルシューティング」とエラー集の依存関係の競合、選定の指針とバージョン管理）は、「トラブルシューティング」をなくし、エラー集の要点から22-20・22-21を参照する形にして解消した（2026-11-11に解消）
- 「よくあるエラーと対処法」の分量が章の4分の1を占めていた問題は、詳細を付録Hへ移して解消した（2026-11-09）
- 22-15（Lombok）の実行結果は、全文を実行した出力に置き換えていない（Lombokの注釈処理が必要なため。2026-11-08時点の注記のまま）
- 「外部ライブラリ選定の指針」の冒頭で「機能性、信頼性、保守性、ライセンスの4つの観点」と述べるが、小見出し（成熟度と信頼性、ライセンス、依存関係の管理、セキュリティ、組み合わせ例）と対応していない（2026-11-12に解消）
- 「クラスパスとは」は定義だけで、`-cp`オプションの使い方を示さない（2026-11-12に解消）

## 節ごとの要約

- 本章の学習目標（L3–31）
    + Javadoc（仕組みと記述）、外部ライブラリの選択基準とライセンス、Mavenを例にしたビルドツールの役割、依存関係とバージョン管理の5項目
    + 必須として第4章・第13章・第14章とHTMLの基礎、推奨として第21章・JSON・開発プロセス
- Javadocによるドキュメント（L32–164）
    + Javadocコメントの書き方: `/** */`の形式と、addメソッドに付けたJavadoc例（22-1）
    + 主要なJavadocタグ: @param、@return、@throws、@author、@version、@since、@see、@deprecatedの表。22-2で使う`{@code}`、`{@link}`、`<pre>`などのインラインタグは説明がない
    + 実践的なJavadocの例: Taskクラスに網羅的なJavadocを付けた例（22-2）
    + Javadocの生成方法: javadocコマンドのオプション（22-3）とIntelliJ IDEAの手順
- 外部ライブラリの利用（L165–1073）
    + オープンソースエコシステムの歴史（年表）
    + ライブラリ利用の技術的利点: 再利用（DRY）、品質、開発速度、標準化、保守を文章で説明する
    + クラスパスとは: JVMがクラスを探す場所としての定義と、JARファイルの説明。JARの作り方は第23章へ誘導
    + 依存関係管理ツール: Mavenの設計原則4つを文章で、依存関係解決の手順（nearest wins、スコープ）を番号付きリストで説明し、図（chapter22-maven-dependency）とpom.xmlへのGsonの記述（22-4）を示す。pom.xmlの全体構成、ディレクトリ規約、ライフサイクル（compile、test、package）は説明しない
    + Gson: @SerializedName、transientによる除外、GsonBuilderによる整形出力（22-5）
    + Jackson: 依存関係（22-6）、@JsonProperty、@JsonIgnore、TypeReferenceによるジェネリック型のデシリアライズ（22-7）
    + Apache Commons: Commons Lang（22-8、22-9）とCommons IO（22-10、22-11）
    + OkHttp: 依存関係（22-12）、同期GET/POSTと非同期リクエスト（22-13）
    + Lombok: 依存関係（22-14）、@Data、@Builder、@NonNullなど（22-15）、個別アノテーション（22-16）
    + Guava: 依存関係（22-17）、不変コレクション、Multimap、BiMap、Table、Splitter/Joiner、キャッシュ（22-18）
    + 外部ライブラリ選定の指針: 成熟度と信頼性、ライセンス（22-19、Apache 2.0・MIT・GPL・LGPLを文章で説明）、testスコープとpropertiesによるバージョン一元管理（22-20、第21章のJUnit・Mockitoに触れる）、OWASP Dependency Check（22-21）、よく使われる組み合わせの表
    + 実践的な開発フロー: mvnコマンドの一覧（22-22）
- よくあるエラーと対処法（L1074–1097）
    + 本文に挙げるエラー: Javadocの生成エラー、依存関係の競合（dependency:treeとexclusions）、バージョン管理の問題（22-20・22-21を参照）、APIの非互換性、クラスパスの問題、設定ファイルの読み込みと型変換、ライブラリの組み合わせ。詳細は`appendix/h-common-errors/chapters/chapter22.md`
- まとめ（L1098–1151）
    + 本章で学んだ技術の核心: Javadoc、外部ライブラリ、依存関係管理、エコシステム。「文芸的プログラミング」は本文に出てこない用語で、「40万以上のアーティファクト」は出典のない数値（2026-11-12に解消）
    + ドキュメント化の技術的価値（効果を4つ挙げる）
    + 依存関係管理の進化: 手動JAR → Maven/Ivy → Gradle → JPMSの世代区分。Gradle・JPMSは本文で扱っていない
    + セキュリティとコンプライアンス: 脆弱性管理、ライセンス遵守、サプライチェーン、GDPR・SOC2
- 章末演習（L1152–1172）
    + リンクは`exercises/chapter22/`。基礎（Javadoc生成）、発展（Mavenプロジェクトと外部ライブラリ）、チャレンジ（複数ライブラリの組み合わせ）。第23章への導線

## 他章との関係

- 第16章（ネットワーク）: 16-11がJacksonを使い、本章へ誘導する。標準のHttpClientとOkHttpの比較や、本章から第16章への参照はない
- 第21章（ユニットテスト）: JUnit・Mockitoの導入を本章へ誘導する。22-20の前でJUnit・Mockitoをtestスコープで加えると述べる
- 第23章（ビルドとデプロイ）: クラスパスの節からJARの作り方へ誘導する
- 付録G（高度なビルドとデプロイ）: Maven/Gradleによる自動化を扱う。説明の分担（本章は依存関係管理、付録Gはビルド自動化）を明確にする必要がある
- 第8章（レコード）: データクラスのボイラープレート削減を扱う。Lombokの@Dataと役割が重なるが、本章からレコードへの言及がない
- 第9章（コレクション）・第6章（不変性）: `List.of`などの標準の不変コレクションと、Guavaの不変コレクションの関係に触れていない
- 第14章（ファイルI/O）: NIOのFilesと、Commons IOのFileUtilsの比較がない
