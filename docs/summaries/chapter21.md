# 第21章 ユニットテストと品質保証 要約

行番号・サンプルコード番号の正確な対応は `docs/book-index/chapter21-unit-testing.md` を参照する。

## 章の概要

- 単体テストの意義、AAAパターン、密結合がテストを妨げる理由、DI（コンストラクタ・セッター・フィールドインジェクション）とスタブによる差し替え、TDDのサイクル、JUnit 5とMockito、FIRST原則、CIとカバレッジを扱う
- 中心の題材はCalculatorとUserService/UserRepository。JUnitを使わない手動テストでAAAとスタブを示してから、JUnit・Mockitoへ進む
- 758行と短く、各トピックは概観にとどまる
- 書籍全体でJUnit、Mockito、DI、TDDを扱うのは本章だけで、他章との重複はほぼない

## 構成上の問題

- 導入が三重になっている
    + 「本章の学習目標」（L3–13）、「この章で学ぶこと」（L14–54）、「はじめに」（L55–60）がそれぞれ章の狙いを述べる。学習目標の5項目は「この章で学ぶこと」でほぼ同じ文言で繰り返される
    + 他章の形式（「本章の学習目標」の下にH3「この章で学ぶこと」「この章を始める前に」）とも異なり、ここではH2が2つ並ぶ
- 「この章で学ぶこと」で予告しているのに本文で扱っていない内容
    + AssertJ（L21）
    + レガシーコードへのテスト追加とリファクタリング（L29）
    + BDD（行動駆動開発）（L31）
    + カバレッジ80%は21-15の設定値として出るだけで、カバレッジの種類や読み方の説明はない（L30）
    + 「品質保証のプロセスを主導」「組織全体の開発効率を改善」（L36）は入門書の目標として過大
- 前提知識と章順の矛盾
    + 推奨知識に第22章（Maven、Gradle）を挙げる（L51）が、本章が先に来る。21-14、21-15はGradle（`./gradlew test`、build.gradle）を前提にしており、ビルドツールは第23章で本格的に扱う
    + JUnit・Mockitoの依存関係をプロジェクトに追加する方法がどこにも書かれていない（第22章にもJUnitの記述はない）。読者は21-11以降を実行できない
- TDDの実践例が1サイクルだけ
    + Red（21-9）とGreen（`return 0;`の21-10）のあと、Refactoringは「不要」として終わる。三角測量や2つ目のテストがなく、サイクルを回す感覚が伝わらない
- 「章末演習」（L649）のあとに「よくあるエラーと対処法」が続き、「次のステップ」で終わったあとに本文が再開する

## 節ごとの要約

- 本章の学習目標（L3–13）
    + 単体テストの重要性、JUnit、TDD、疎結合とDI、モックの5項目
- この章で学ぶこと（L14–54）
    + 学習目標を散文で拡張し、AssertJ、CI、レガシーコード、カバレッジ80%、BDDまで予告する
    + 前提は第4章・第7章・第13章、推奨は第15章・第22章・デザインパターン
- はじめに（L55–60）
    + テストの重要性と、疎結合・DIを学ぶことを再度述べる
- 単体テストの基礎（L61–110）
    + 単体テストの定義と4つのメリット（早期発見、リファクタリングの安全網、動く仕様書、開発の高速化）
    + バグ修正コストをコメントだけで示すコード（21-1）と、その「実行結果」として概念説明を載せている
- テストの基本形（AAAパターン）（L111–197）
    + Arrange・Act・Assertの3ステップ
    + テスト対象のCalculator（21-2）と、JUnitを使わない手動テスト（21-3）
- テストを妨げる「依存関係」（L198–236）
    + UserServiceが内部でUserRepositoryを`new`する密結合の例（21-4）。テストするとDB接続が走ることを問題として示す
- 疎結合設計（Dependency Injection）（L237–306）
    + インターフェイスへの依存、DIとIoCの定義
    + コンストラクタインジェクション（推奨、21-5）、セッターインジェクション（21-6）、フィールドインジェクション（コードなし、フレームワーク向け）とそれぞれの長所短所
- DIによるテスト容易性の向上（L307–401）
    + UserRepositoryをインターフェイス化したUserService（21-7）
    + 手書きのスタブリポジトリでUserServiceをDBなしでテストする（21-8）
- テスト駆動開発（TDD）（L402–450）
    + Red・Green・Refactoringのサイクル
    + StringCalculatorの空文字列で0を返すテスト（21-9）と最小実装（21-10）
- JUnitによる効率的なテスト（L451–528）
    + JUnit 5の`@Test`、`@BeforeEach`、`assertEquals`、`assertThrows`（21-11）
    + Mockitoの`@Mock`、`when().thenReturn()`、`verify()`（21-12）
- テストのベストプラクティス（L529–571）
    + FIRST原則
    + `@Nested`と`@DisplayName`による正常系・異常系の構造化（21-13）
- 継続的インテグレーション（CI）との統合（L572–629）
    + GitHub Actionsでプッシュごとにテストを実行するワークフロー（21-14）
    + JaCoCoで80%のカバレッジを要求するbuild.gradle（21-15）
- まとめ（L630–648）
    + 単体テスト、疎結合、DI、TDD、ツール活用の5点
- 章末演習（L649–672）
    + 演習リンクは`exercises/chapter21/`。基礎（JUnit）、発展（TDD）、チャレンジ（モック）の3段構成
    + 次のステップとして第22章を案内する
- よくあるエラーと対処法（L673–758）
    + 境界値・異常値のテスト不足（21-16）、浮動小数点の厳密比較（21-17）、モックの設定不足（21-18）、テスト間の依存（21-19）

## 校正で見つけた個別の問題

- L410–412: TDDサイクルの項目に絵文字（🔴🟢🔵）を使っている（ルール違反）
- L115–117、L533–537: 「Arrange（準備）: 説明」「Fast（高速）: 説明」と項目名と説明をコロンでつなぐ形式で、階層化リストのルールに反する
- L282: 「必須の依存性にはありません」は自動変換による誤り（元は「向いていません」と推測される）
- L680、L722: 「テストしていありません」「設定されていありません」は自動変換による誤り（「していません」）
- L705、L745: 「##### 問題」の下の1行が体言止めに句点を付けた断片
- L73: 単体テストで手戻りコストを「リリース後の100分の1以下に抑えます」と断定しており、根拠がない
- 21-1: コメントだけのコードにサンプルコード番号と「実行結果」を付けている。21-2も実行できないクラスに「実行結果」を付けている
- 21-11: Calculatorの`divide`をテストしているが、21-2のCalculatorには`add`しかない
- 21-12: `@Mock`を使っているが`@ExtendWith(MockitoExtension.class)`も`MockitoAnnotations.openMocks`もないため、モックが初期化されずNullPointerExceptionになる。`assertEquals`のstatic importもない
- 21-14: `actions/setup-java@v2`は`distribution`の指定が必須で、このままでは失敗する。`checkout@v2`も古い
- 21-15: JaCoCoの`xml.enabled`/`html.enabled`はGradle 8で削除済み（`required`を使う）
- 21-19: カウンタをローカル変数で初期化するだけの例で、テスト間の依存（共有状態）を解消する例になっていない
- L3–13とL14–36: 学習目標の文言がほぼそのまま重複している
- L259: DIの説明で「テスト時にはモックオブジェクトを」と書くが、直後の実例（21-8）はスタブで、用語の使い分けがない
