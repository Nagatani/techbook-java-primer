# 付録E チャレンジ課題

## 学習目標

- 外部キーでつながった複数のテーブルを設計し、`INNER JOIN`で結合して検索する
- 「在庫を確かめる・貸出中にする・貸出の記録を足す」のような複数の更新を、1つのトランザクションにまとめる
- 決まりに合わないとき（貸出中の本、冊数の上限）を自分の例外クラスで表し、データベースの障害（`SQLException`）と分けて扱う
- 日付の列を`LocalDate`で読み書きし、返却期限と延滞日数を計算する
- バッチ処理での一括登録と、`GROUP BY`での集計を組み合わせる

## 課題一覧

### 課題1: 図書の貸出管理

**ファイル**（このフォルダーのファイルは解答例です）:

```
challenge/
├── Book.java             本（レコード）
├── Member.java           利用者（レコード）
├── Loan.java             貸し出している1冊（レコード）
├── LoanException.java    貸出・返却の決まりに合わないときの例外
├── LibraryDatabase.java  テーブルの作成と、本・利用者の一括登録
├── LoanService.java      貸出・返却と、貸出状況の検索
└── LibraryApp.java       mainメソッド
```

大学の図書室の貸出と返却を、データベースで管理するプログラムを作成してください。
日付は`LocalDate`の固定の値を使い、現在の日付は使いません。

**要求仕様**:

- テーブル（`LibraryDatabase.createTables`）
    - `books`は本のID（`B001`など）・題名・著者・貸出中かどうか（`BOOLEAN`）を持つ
    - `members`は利用者のID・名前を持つ
    - `loans`は貸出のID（データベースが振る）・本のID・利用者のID・貸した日・返却期限・返した日・延滞料金を持つ。本のIDと利用者のIDには外部キーの制約を付ける。返した日と延滞料金は、返却するまでNULLにする
- 一括登録（`LibraryDatabase`）
    - `registerBooks`と`registerMembers`は、`addBatch`・`executeBatch`でまとめて登録し、登録した数を返す。途中で失敗したら1件も登録しない
- 貸出（`LoanService.lend(利用者のID, 本のID, 貸す日)`）
    - 返却期限は貸した日の14日後
    - 次のときは`LoanException`を投げ、データベースを何も変えない
        - 利用者が登録されていない
        - その利用者が返していない本がすでに3冊ある
        - 本が貸出中である、または本が存在しない
    - 本を貸出中にする更新（`UPDATE books ... WHERE id = ? AND on_loan = FALSE`）と、`loans`への行の追加を、1つのトランザクションで行う
    - 貸し出した1冊を`Loan`で返す
- 返却（`LoanService.giveBack(本のID, 返す日)`）
    - 返した日と延滞料金（返却期限を過ぎた日数 × 10円）を`loans`に記録し、本を貸出中でなくす。2つの更新を1つのトランザクションで行う
    - 貸し出していない本なら`LoanException`を投げる
    - 題名・利用者の名前・延滞日数・延滞料金を、レコード`ReturnResult`で返す
- 検索と集計（`LoanService`）
    - `currentLoans()`は貸出中の本を、`overdueLoans(日付)`はその日の時点で返却期限を過ぎている本を、返却期限の順に返す。どちらも`loans`・`books`・`members`を`INNER JOIN`し、題名と利用者の名前を含む`Loan`にする
    - `searchBooks(キーワード)`は、題名か著者にキーワードを含む本を、貸出中かどうかとともに返す
    - `memberStats()`は、利用者ごとの貸出回数（返却済みを含む）と延滞料金の合計を、回数の多い順に返す
- `LibraryApp`
    - 本6冊と利用者3人を登録し、貸出・検索・期限切れの確認・返却・集計を、決まった日付で順に行う

## 実装のヒント

```java
public Loan lend(int memberId, String bookId, LocalDate today) throws SQLException, LoanException {
    boolean originalAutoCommit = connection.getAutoCommit();
    connection.setAutoCommit(false);
    try {
        // 利用者と冊数を確かめ、本を貸出中にして、loansに行を足す
        connection.commit();
        // ...
    } catch (SQLException | LoanException e) {
        connection.rollback();   // 決まりに合わなかったときも取り消す
        throw e;
    } finally {
        connection.setAutoCommit(originalAutoCommit);
    }
}
```

- 「本が貸出中でないか調べる」と「貸出中にする」を別々のSQLにすると、その間にほかの人が同じ本を借りるおそれがある。`UPDATE ... WHERE id = ? AND on_loan = FALSE`の変更した行数で判定すれば、確かめることと書き換えることを1つのSQLで行える
- 変更した行が0のときは、本がないのか貸出中なのかがわからない。`SELECT`で本を探し直して、理由を分ける
- `LoanException`は`Exception`を継承した検査例外にする。呼び出す側は、利用者に理由を伝える`LoanException`と、プログラムやデータベースの障害を表す`SQLException`を分けて`catch`できる
- 延滞日数は`ChronoUnit.DAYS.between(返却期限, 返した日)`で求め、0未満なら0にする（java.time APIは付録Fで紹介している）
- `SUM(l.fee)`は、対象の行がすべてNULLならNULLを返す。`getInt`はNULLを0として返すので、この集計ではそのまま使える
- 列の名前`day`・`month`などはSQLの予約語なので使わない。解答例では`loaned_on`・`due_on`・`returned_on`とした

## 応用のポイント

1. トランザクションの範囲
    - 1回の貸出・返却で行う複数の更新を、ひとまとまりにする。途中で失敗したときに「本は貸出中なのに貸出の記録がない」状態が残らない
2. 例外の使い分け
    - 決まりに合わないことは`LoanException`、データベースの障害は`SQLException`で知らせ、mainでの扱いを分ける
3. 結合と集計
    - 画面に出す題名や名前はIDから`INNER JOIN`で引き、同じ情報を複数のテーブルに持たない

## 発展（任意）

- 予約の機能を足す。貸出中の本に予約を入れられるようにし、返却されたら予約した人にだけ貸し出せるようにする
- 延滞料金に上限（1冊500円まで）を設ける。どのクラスのどのメソッドを変えるのがよいかを考える
- `LoanService`を、付録EのDAOパターンにならって`BookDao`・`LoanDao`に分ける。トランザクションの`commit`と`rollback`を、どのクラスで呼ぶのがよいかを考える
