# 5. アルゴリズム解析と計算複雑度

## この項目で学ぶこと

同じ問題を解くプログラムでも、データが10件のときと100万件のときでは、かかる時間の伸び方がまったく違うことがあります。
この項目では、その伸び方を数式で表して比べる方法を学びます。

- 計算量（時間計算量・空間計算量）とは何か
- O記法（ビッグオー記法）と、Ω・Θの意味
- 最悪・平均・最良の場合と、償却解析
- ループと再帰の計算量の求め方
- JavaのコレクションAPIの計算量の読み方
- P と NP の問題（入口だけ）

## なぜ必要か

### 測るだけでは足りない

プログラムの速さを知るいちばん素直な方法は、実行して時間を測ることです。
しかし、測った時間はコンピューターの性能、JVMの状態（JITコンパイルが済んでいるかどうか）、ほかに動いているプログラムなどで変わります。
しかも、手元で試した入力の大きさでの結果しかわかりません。
1万件で0.1秒だったプログラムが100万件で何秒かかるかは、測った時間からは読み取れません。

そこで、実行時間そのものではなく「入力の大きさnに対して、基本的な操作（比較・代入など）が何回行われるか」を数え、nが大きくなったときの増え方で比べます。
この考え方が計算量（computational complexity）の解析です。
コンピューターが10倍速くなっても、増え方の違いは埋まりません。
n²回の操作が要るアルゴリズムは、nが10倍になると100倍の時間がかかるからです。

### 歴史的な背景

アルゴリズムを数学的に解析する分野は、Donald Knuthの『The Art of Computer Programming』（第1巻は1968年）によって体系づけられました。
O記法そのものは数学（整数論）の記法で、Paul Bachmann（1894年）が使い、Edmund Landauが広めたものです。
Knuthは1976年の論文「Big Omicron and Big Omega and Big Theta」で、アルゴリズムの解析でO・Ω・Θを使い分けることを提案しました。

## 基本操作を数える

C言語で配列の要素を探す関数を書いたことがあるでしょう。
先頭から順に調べる線形探索は、見つからない場合にn個の要素すべてと比べます。
並べてある配列を半分ずつに絞る二分探索は、1回比べるたびに候補が半分になるので、比較はおよそlog₂n回で済みます。

このリポジトリの`src/main/java/com/example/theory/algorithms/OperationCounting.java`は、要素どうしを比べた回数を数えて表にします。
時間ではなく回数を数えるので、どのコンピューターで実行しても同じ結果になります。
比較のたびにカウンターを1つ増やすメソッドを用意し、各アルゴリズムはそのメソッドを通して比べています。

```java
private static boolean less(int a, int b) {
    comparisons++;
    return a < b;
}
```

`appendix/c-theoretical-foundations/`でコンパイルしたあと、次のようにクラスを直接指定して実行します（`java -cp out com.example.theory.Main algorithms`の「Operation Counting」の部分にも同じ表が表示されます）。

```bash
javac -d out $(find src -name '*.java')
java -cp out com.example.theory.algorithms.OperationCounting
```

出力は次のとおりです。

```
Number of comparisons (worst case for search: target not found)
       n     linear   binary       bubble      merge
      10         10        6           45         15
     100        100       12         4950        316
    1000       1000       18       499500       4932
   10000      10000       26     49995000      64608
```

列の意味と読み方は次のとおりです。

- linear（線形探索）
    + nが10倍になると、比較の回数もちょうど10倍になる
- binary（二分探索）
    + nが10倍になっても、回数は6ずつしか増えない
    + この実装はループ1回で「等しいか」「小さいか」の2回比べるので、ループの回数は表の半分（n=10000で13回）になる。log₂10000はおよそ13.3である
- bubble（バブルソート）
    + 逆順に並んだ配列で、n(n-1)/2回比べる。nが10倍になると、回数はおよそ100倍になる
- merge（マージソート）
    + nが10倍になると、回数は10倍よりすこし多く増える。n log n の増え方である

n=10ではバブルソート（45回）とマージソート（15回）の差は3倍ですが、n=10000では約770倍に開きます。
小さなデータで試しただけでは、この差に気づけません。

## O記法の定義

### 定義

関数f(n)とg(n)について、ある正の定数cとn₀があって、n₀以上のすべてのnでf(n) ≤ c·g(n)が成り立つとき、f(n) = O(g(n))と書きます。
「nが十分大きいところでは、fはgの定数倍で上から抑えられる」という意味です。

たとえば、バブルソートの比較回数f(n) = n(n-1)/2 = n²/2 - n/2は、すべてのn ≥ 1でn²/2 - n/2 ≤ n²なので、c = 1、n₀ = 1としてf(n) = O(n²)です。

この定義から、次の2つの規則が出てきます。

- 定数倍を無視する
    + 3n² も n²/2 も O(n²) である。定数倍はコンピューターの速さや実装の細部で変わるので、増え方の比較には使わない
- いちばん速く増える項だけを残す
    + n² + 100n + 1000 は O(n²) である。nが大きくなると n² 以外の項は比べものにならなくなる

O記法の「=」は等しいという意味ではなく、「右辺の集合に属する」という意味です。
O(n²)は「定数倍でn²以下に収まる関数の集まり」で、f(n) = O(n²)はf(n) ∈ O(n²)の慣用的な書き方です。
そのため、n = O(n²)は正しい式ですが、O(n²) = nとは書きません。

### Ω と Θ

O記法は上限を表します。
下限と、上下両方を表す記法もあります。

| 記法 | 意味 | 定義（n ≥ n₀ のすべてのnで） |
|------|------|------|
| f(n) = O(g(n)) | 上限。fはgより速くは増えない | f(n) ≤ c·g(n) |
| f(n) = Ω(g(n)) | 下限。fはgより遅くは増えない | f(n) ≥ c·g(n) |
| f(n) = Θ(g(n)) | fとgは同じ速さで増える | O(g(n))かつΩ(g(n)) |

バブルソートの比較回数n(n-1)/2はΘ(n²)です。
一方、線形探索の比較回数はO(n²)と書いても誤りではありません（上限としては正しい）が、情報が少なくなります。
日常の会話や多くの文書では、Θの意味で「O(n²)」と言うことがよくあります。
厳密な議論をするときは区別してください。

### よく出てくる増え方

小さい順に並べると次のようになります。

| 記法 | 名前 | 例 | n=1000のおよその値 |
|------|------|------|------|
| O(1) | 定数時間 | 配列の添え字アクセス | 1 |
| O(log n) | 対数時間 | 二分探索 | 10 |
| O(n) | 線形時間 | 線形探索、配列の合計 | 1,000 |
| O(n log n) | | マージソート | 10,000 |
| O(n²) | 2乗時間 | バブルソート、2重ループで全組を調べる | 1,000,000 |
| O(2ⁿ) | 指数時間 | n個の要素の部分集合をすべて調べる | 約10³⁰¹ |

log nの底は書かないのが普通です。
log₂n = log₁₀n / log₁₀2 のように、底の違いは定数倍の違いにすぎないからです。

## 計算量の求め方

### ループ

ループの計算量は「ループの回数 × 1回あたりの計算量」で求めます。

- 1重のループでn回まわる
    + O(n)
- 2重のループで、外側も内側もn回まわる
    + O(n²)
- 内側の回数が外側の変数で変わる（`for (j = 0; j < n - i - 1; j++)`など）
    + 合計を求める。バブルソートは (n-1) + (n-2) + … + 1 = n(n-1)/2 で O(n²)
- 1回ごとに範囲が半分になる
    + O(log n)。nを何回半分にすると1になるかが log₂n である

`src/main/java/com/example/theory/complexity/TimeComplexityExamples.java`の`bubbleSort`には、ループごとの回数と合計の式がコメントで書いてあります。

### 再帰と漸化式

再帰するアルゴリズムでは、計算量を漸化式で表します。
マージソートは、配列を半分に分けてそれぞれを並べ（大きさn/2の問題を2つ）、2つの並んだ列を1つにまとめます（O(n)）。
そのため、時間T(n)は次の式を満たします。

```
T(n) = 2T(n/2) + cn
```

この式は、再帰の木を描くと解けます。

```
レベル0:            n               → 合計 cn
レベル1:        n/2     n/2         → 合計 cn
レベル2:     n/4 n/4 n/4 n/4        → 合計 cn
  ...
レベルlog₂n:  1 1 1 ... 1 （n個）    → 合計 cn
```

各レベルの仕事の合計はcnで、レベルの数はlog₂n + 1なので、T(n) = Θ(n log n)です。
T(n) = aT(n/b) + f(n)の形の漸化式は、アルゴリズムの教科書で「マスター定理」と呼ばれる公式で、多くの場合まとめて解けます。

`TimeComplexityExamples.java`の`mergeSort`には、この漸化式がコメントで書いてあります。

### 実務でよく出会うO(n²)

計算量の解析が役に立つのは、ソートを自作するときよりも、何気なく書いたコードが遅い原因を見つけるときです。
Javaでよくある例を挙げます。

- ループのなかで文字列を`+`で連結する
    + `String`は不変なので、連結のたびにそれまでの文字列全体をコピーした新しい文字列を作る。長さ1, 2, …, nの文字列を作るので、合計はO(n²)になる
    + `StringBuilder`の`append`は内部の配列に追記するので、n回でO(n)になる
- `LinkedList`を`get(i)`でループする
    + `LinkedList`の`get(i)`は先頭（または末尾）からたどるのでO(n)である。`for (int i = 0; i < list.size(); i++) list.get(i)`はO(n²)になる。拡張for文（イテレーター）ならO(n)で済む
- ループのなかで`List.contains`や`List.remove(Object)`を呼ぶ
    + どちらもO(n)なので、ループ全体はO(n²)になる。存在の確認が多いなら`HashSet`を使う

文字列の連結の例は、次のようなコードです。

```java
// 文字列の連結を繰り返す: 毎回、それまでの文字列全体をコピーする → O(n²)
static String joinSlow(int n) {
    String s = "";
    for (int i = 0; i < n; i++) {
        s = s + "x";
    }
    return s;
}

// StringBuilderは内部の配列に追記する（容量は必要に応じて広げる） → O(n)
static String joinFast(int n) {
    StringBuilder sb = new StringBuilder();
    for (int i = 0; i < n; i++) {
        sb.append("x");
    }
    return sb.toString();
}
```

## 最悪・平均・最良の場合

同じnでも、入力の中身によって手間が変わるアルゴリズムがあります。
線形探索は、探す値が先頭にあれば1回、なければn回比べます。
そこで、次の3つを区別します。

- 最悪の場合（worst case）
    + 大きさnのあらゆる入力のなかで、いちばん手間がかかる入力での計算量。保証として使える
- 平均の場合（average case）
    + 入力の分布（たとえば「すべての並び方が同じ確率で現れる」）を仮定したときの期待値。仮定が現実に合っているかが問題になる
- 最良の場合（best case）
    + いちばん手間の少ない入力での計算量。これだけを見ても性能の保証にならない

クイックソートはこの違いがはっきり出る例です。
ピボット（分割の基準にする要素）で配列を2つに分けて再帰しますが、分割がおよそ半々なら平均Θ(n log n)、毎回いちばん端の要素がピボットになると、分割が n-1 と 0 になってΘ(n²)になります。
`TimeComplexityExamples.java`の`partition`は区間の末尾をピボットにするので、すでに並んでいる配列が最悪の入力になります。
すでに並んでいるデータを並べ直すことは実務で珍しくないので、ライブラリの実装はピボットの選び方を工夫しています。

`OperationCounting`の表は、探索については「見つからない」という最悪の場合、ソートについては逆順の配列での回数を数えています。
バブルソートの比較回数は入力の並び方によらずn(n-1)/2ですが、マージソートの比較回数は入力によって変わります（表のn=10000の64608回は、逆順の入力での値です）。

## 償却解析

### 1回だけ見ると高いが、平均すると安い操作

`ArrayList`の`add`は、内部の配列に空きがあればO(1)で終わります。
空きがなければ、大きな配列を作って全要素をコピーするので、そのときだけO(n)かかります。
最悪の場合だけを見ると「`add`はO(n)」ですが、これでは`add`をn回呼ぶとO(n²)かかるように見えてしまい、実態に合いません。

償却解析（amortized analysis）は、操作を1回ずつではなく、操作の列全体の合計で考える方法です。
n回の操作の合計がT(n)なら、1回あたりの償却コストはT(n)/nです。
この考え方は、Robert Tarjanが1985年の論文「Amortized Computational Complexity」で体系的に示しました。

### 容量を2倍にする動的配列

容量1から始めて、いっぱいになるたびに容量を2倍にする配列にn個の要素を追加する場合を考えます。
要素を書き込むコストを1、コピーするコストを1要素あたり1とします。

- 書き込みはn回で、合計n
- コピーは容量が2⁰から2ᵏ（2ᵏ < n）までの2の累乗のときに起き、合計は2⁰ + 2¹ + … + 2ᵏ = 2ᵏ⁺¹ - 1 < 2n

合計は3n未満なので、1回あたりの償却コストはO(1)です。
等比数列の和が最後の項の2倍未満に収まることが、この結果の鍵です。

もし容量を「2倍」ではなく「10ずつ」増やすと、コピーは10, 20, 30, …で起き、合計はおよそn²/20になります。
償却コストはO(n)になり、n回の追加はO(n²)です。
倍率は2でなくてもかまいませんが（1.5倍でもO(1)になります）、一定の倍率で増やすことが必要です。

このリポジトリの`src/main/java/com/example/theory/structures/DynamicArray.java`が、容量を2倍にする動的配列と、そのコストを数えるデモです。
`java -ea -cp out com.example.theory.Main structures`を実行すると、「Dynamic Array Amortized Analysis」の部分にn=100での合計コスト・容量を広げた回数・1回あたりのコストが表示されます。

```
--- Dynamic Array Amortized Analysis ---
n = 100
Total cost: 227
Resize count: 7
Amortized cost per operation: 2.27
```

容量は1→2→4→…→128と7回広がり、コピーの合計は1 + 2 + … + 64 = 127です。
書き込みの100と合わせて227になり、1回あたり2.27で、上の見積もり（3未満）に収まっています。

### Javaのドキュメントの書き方

`ArrayList`のJavadocには、「容量を増やす方針の詳細は、要素の追加が一定の償却時間でできるということ以外は定めない」という趣旨の記述があります。
つまり、償却O(1)は仕様として約束されていますが、何倍に広げるかは実装に任されています。
OpenJDKの実装は約1.5倍に広げますが、それに依存したコードを書いてはいけません。

あらかじめ要素の数がわかっているなら、`new ArrayList<>(n)`で容量を指定すると、途中で広げる処理そのものを省けます。

### ハッシュテーブル

`HashMap`の`get`・`put`が「O(1)」と言われるのも、平均と償却の両方の意味を含んでいます。

- 平均の意味
    + ハッシュ関数がキーをばらばらの位置に散らすと仮定したとき、1つの位置（バケット）に入る要素の数の期待値は、負荷率（要素の数÷バケットの数）で抑えられる。負荷率を一定以下に保てば、探す手間は平均O(1)になる
- 償却の意味
    + 負荷率が上限（`HashMap`の既定は0.75）を超えると、バケットの数を増やして全要素を入れ直す。これは動的配列と同じ理由で償却O(1)になる
- 最悪の場合
    + すべてのキーが同じ位置に集まると、探す手間はO(n)になる。`hashCode`が同じ値ばかり返すクラスをキーにしたときに起きる

`src/main/java/com/example/theory/structures/HashTable.java`は、チェイン法（同じ位置の要素を連結リストでつなぐ方法）のハッシュテーブルで、要素を追加する前に負荷率が0.75以上になっていれば、バケットを2倍にします。
`Main structures`の「Hash Table Performance」に、負荷率と最長のチェインの長さが表示されます。

`hashCode`の書き方が計算量を左右することは、第5章で学ぶ`equals`と`hashCode`の規約とあわせて覚えておいてください。

## 空間計算量

計算量は時間だけでなく、使うメモリの量についても考えます。
これを空間計算量（space complexity）と呼びます。
ふつうは入力そのものを除いた、アルゴリズムが追加で使うメモリ（補助領域）で数えます。

- バブルソート
    + 添え字と交換用の変数しか使わないのでO(1)。元の配列のなかで並べ替える方式を in-place と呼ぶ
- マージソート（配列をまとめる処理で作業用の配列を使う）
    + O(n)
- 再帰
    + 呼び出しのたびにスタックに領域を積むので、再帰の深さぶんのメモリを使う。マージソートの再帰の深さはO(log n)である

`TimeComplexityExamples.java`の`quickSortIterative`は、再帰の代わりに未処理の区間をスタックに積む in-place のソートで、スタックの大きさが空間計算量になります（平均O(log n)、最悪O(n)）。
`mergeSortWithCopy`は、分けるたびに新しい配列を作る書き方で、同時に使う配列の合計はO(n)です。

時間と空間は、しばしば交換（トレードオフ）の関係になります。
計算結果を表に覚えておいて再利用するメモ化は、メモリを使って時間を減らす典型例です。
逆に、メモリが限られた環境では、時間がかかっても補助領域の少ない方法を選びます。

Javaでは、深い再帰で`StackOverflowError`が起きることがあります。
スレッドのスタックの大きさには上限があるので、再帰の深さがO(n)になる処理（連結リストを再帰でたどるなど）は、nが大きいときにループで書き直します。

## JavaのAPIの計算量を読む

Javaの標準ライブラリは、Javadocに計算量を書いていることが多いので、使う前に確かめる習慣をつけてください。

| 操作 | 計算量 | 根拠・注意 |
|------|------|------|
| `ArrayList.get(i)` | O(1) | 配列の添え字アクセス |
| `ArrayList.add(e)`（末尾） | 償却O(1) | Javadocに記述がある |
| `ArrayList.add(0, e)`（先頭） | O(n) | 後ろの要素をすべてずらす |
| `LinkedList.get(i)` | O(n) | 先頭か末尾からたどる |
| `HashMap.get` / `put` | 平均O(1) | ハッシュ関数がよく散らす前提 |
| `TreeMap.get` / `put` | O(log n) | 赤黒木。Javadocに記述がある |
| `Collections.sort` / `List.sort` | O(n log n) | 安定なソート（等しい要素の順序を保つ） |
| `Arrays.binarySearch` | O(log n) | 配列が並んでいることが前提 |

`Arrays.sort`のオブジェクトの配列版と`List.sort`は、Tim PetersがPython用に作ったソート（TimSort）をもとにした安定なマージソートで、Javadocにそのことが書かれています。
すでにほぼ並んでいるデータでは、n log nより少ない比較で済みます。

コレクションの選び方そのものは第9章で学びます。

## よくある誤解・注意点

- O(1)は速いという意味ではない
    + nによらず一定というだけで、その一定の時間が長いこともある。`HashMap`の`get`はハッシュ値の計算を含むので、要素が数個なら配列を順に調べるほうが速いこともある
- 計算量が小さいほうが、つねに速いわけではない
    + O記法は定数倍を捨てるので、nが小さいところではO(n²)のほうが速いことがある。実際、ライブラリのソートは、小さな区間では挿入ソート（O(n²)）に切り替える
- 実行時間の計測はO記法の代わりにならないし、O記法も計測の代わりにならない
    + O記法は増え方を予測する道具で、実際の速さはメモリのキャッシュやJITコンパイルにも左右される。Javaで速さを比べるときは、JVMの準備運動（ウォームアップ）を考えて計測する。JMHという計測用のライブラリがよく使われる
- 平均O(1)を最悪O(1)と取り違える
    + 外部から受け取った文字列をキーにする`HashMap`では、同じハッシュ値になるキーをわざと大量に送られると、最悪の場合に近づく。OpenJDKの`HashMap`は、1つのバケットの要素が増えると木構造に切り替えて、この場合の悪化を抑えている（実装の詳細であり、仕様ではない）
- 二分探索の中央の計算
    + `(left + right) / 2`は、`left + right`が`int`の最大値を超えると負になる。`left + (right - left) / 2`と書く。Joshua Blochは2006年のブログ記事で、JDKの`Arrays.binarySearch`にもこの誤りがあったことを報告した。`BinarySearchWithSpecs.java`はこの書き方をしている

## P と NP（入口）

ここまでの例は、どれもnの多項式（n、n²、n log nなど）で抑えられる時間で解けました。
しかし、知られているどのアルゴリズムでも、最悪の場合に指数時間かかる問題があります。

例として、部分和問題を考えます。
「整数の集まりと目標の値が与えられたとき、合計がちょうど目標になる部分集合はあるか」という問題です。
部分集合は2ⁿ通りあるので、すべてを調べるとO(2ⁿ)かかります。
一方、「この部分集合です」という答えの候補が示されれば、合計を計算して確かめるのはO(n)で済みます。

この「解くのは難しそうだが、答えを確かめるのは易しい」という性質を、次のように分類します。

- P
    + 多項式時間で解ける判定問題（答えがyesかnoの問題）の集まり
- NP
    + 答えがyesのとき、その証拠（部分和問題なら部分集合）を多項式時間で確かめられる判定問題の集まり。Pの問題はすべてNPにも入る
- NP完全
    + NPのなかでいちばん難しい問題の集まり。NPのどの問題も、多項式時間の変換でNP完全問題に帰着できる。NP完全問題のどれか1つでも多項式時間で解ければ、NPのすべての問題が多項式時間で解ける

Stephen Cookは1971年に、論理式の充足可能性の問題（SAT）がNP完全であることを示しました（Leonid Levinも独立に同様の結果を得ています）。
翌1972年にRichard Karpが、組合せの問題21個がNP完全であることを示し、部分和問題に近いナップサック問題などもそこに含まれています。

P = NPかどうか（NPの問題がすべて多項式時間で解けるのかどうか）は未解決で、クレイ数学研究所が2000年に発表したミレニアム懸賞問題の1つです。
多くの研究者はP ≠ NPだと予想していますが、証明されていません。

実務では、作ろうとしている処理がNP完全問題（スケジュールの最適化や配送経路の最適化など）に当たると気づいたら、厳密な最適解にこだわらない判断をします。
近似アルゴリズムや経験則（ヒューリスティック）で「十分よい解」を求める、入力の大きさを制限する、といった方法です。
気づかずに全探索を書くと、テストの小さなデータでは動き、本番のデータで終わらなくなります。

## 実務での使いどころ

- コードレビューで、ループのなかで呼んでいるメソッドの計算量を確かめる
- データの件数が増えたときに性能が保てるかを、計測の前に見積もる
- コレクションを選ぶ理由を説明する（「存在の確認が多いので、O(n)の`List.contains`ではなく平均O(1)の`HashSet`にする」）
- 外部からの入力の大きさに上限を設けるかを判断する（入力に対してO(n²)以上の処理は、大きな入力で止まったように見える）
