# 1. ソフトウェアクライシスとその解決策

## この項目で学ぶこと

本書では、クラス、カプセル化、インターフェイス、ユニットテストなど、たくさんの技術を学びます。
これらの技術は、ある日まとめて考え出されたものではありません。
「大きなプログラムを、期限どおりに正しく、直しやすく作るにはどうすればよいか」という問題に対して数十年かけて積み重ねられてきた答えです。

この項目では、その出発点になった「ソフトウェアクライシス（software crisis、ソフトウェア危機）」と、それに対して提案されてきた主な解決策を、歴史の順にたどります。
次のことを理解するのが目標です。

- ソフトウェアクライシスとは何を指す言葉か
- 構造化プログラミング、モジュール化と情報隠蔽、オブジェクト指向、開発プロセスの改善が、それぞれどんな問題を解こうとしたか
- 「銀の弾丸はない」という主張の意味と、それが今日の開発にどうつながっているか

## ソフトウェアクライシスとは

### 言葉の由来

1960年代、コンピューターの性能は急速に上がり、それまでより大きなプログラムを動かせるようになりました。
ところが、作るべきプログラムが大きくなるにつれて、開発の遅れ、予算の超過、完成したプログラムの誤りが目立つようになりました。

1968年10月、西ドイツのガルミッシュで、NATO（北大西洋条約機構）の科学委員会が後援する会議が開かれました。
会議の名前は「ソフトウェア工学（Software Engineering）」です。
橋や建物を建てるときのように、ソフトウェアも確立した方法にもとづいて作るべきだという問題意識が、この名前に込められています。
この会議の報告書（Naur と Randell が編集）では、大規模なソフトウェアを作ることの難しさが大きな話題になり、その状況を指して「ソフトウェアクライシス」という言葉が使われるようになりました。
翌1969年にはローマで2回目の会議が開かれています。

1972年には、エドガー・ダイクストラ（Edsger W. Dijkstra）がチューリング賞の受賞講演「謙虚なプログラマー（The Humble Programmer）」で、ソフトウェアクライシスの原因を論じました。
ダイクストラの論点は、機械が強力になったことで、プログラマーが扱わなければならない問題の大きさと複雑さも一緒に増えた、というものです。

### 何が「危機」だったのか

ソフトウェアクライシスは、1つの事件ではなく、次のような症状の集まりを指します。

- 開発が予定より大きく遅れる
- 費用が見積もりを大きく超える
- 完成したプログラムに誤りが多く、利用者の求めるものと違う
- プログラムを直そうとすると、別の箇所が壊れる
- 書いた本人しか中身を理解できず、担当者が替わると保守できない

その根にあるのは「複雑さ」です。
プログラムが大きくなると、部品どうしの関係の数は部品の数よりも速く増えます。
人間が一度に頭に置いておける量には限りがあるので、何も工夫しなければ、ある大きさを超えたところで誰もプログラム全体を把握できなくなります。

この問題をよく表しているのが、フレデリック・ブルックス（Frederick P. Brooks, Jr.）の『人月の神話（The Mythical Man-Month）』（1975年）です。
ブルックスはIBMで大型機のオペレーティングシステムOS/360の開発を率いた経験から、「遅れているソフトウェアプロジェクトに人を追加すると、さらに遅れる」と書きました（ブルックスの法則）。
人が増えると、仕事を教える時間と、人どうしの連絡の手間が増えるためです。
n人のチームでは、2人ずつの連絡の経路が n(n-1)/2 本あります。
5人なら10本、10人なら45本です。
これは、プログラムの部品どうしの関係が増えるのと同じ形をしています。

### 現代にも続く問題

ソフトウェアの誤りが大きな損害につながった例は、その後も記録されています。
よく知られている例に、1996年のアリアン5ロケット初号機の打ち上げ失敗があります。
調査委員会の報告によると、慣性基準装置のソフトウェアが64ビットの浮動小数点数を16ビットの符号付き整数に変換したときにあふれが起き、その例外が処理されずに装置が停止したことが原因でした。
このソフトウェアは前の機種（アリアン4）から引き継いだもので、アリアン4の飛行条件ではあふれない値でした。
「以前は正しく動いていた部品を、前提の違う場所で使った」ことが問題だったわけです。
この「部品が何を前提にしているかを明示する」という考え方は、項目2の抽象データ型や、項目6（[06-formal-specification.md](06-formal-specification.md)）の契約による設計につながります。

## 解決策1：構造化プログラミング

### goto文の問題

1960年代のプログラムは、goto文で処理の流れを自由に飛ばして書くのが普通でした。
次のC言語の関数は、配列から値を探す処理をgoto文だけで書いたものです。

```c
/* 配列aからkeyを探し、見つかった添字を返す（ない場合は-1） */
int find_goto(const int a[], int n, int key) {
    int i = 0;
loop:
    if (i >= n) goto not_found;
    if (a[i] == key) goto found;
    i++;
    goto loop;
found:
    return i;
not_found:
    return -1;
}
```

この程度の長さなら読めますが、ラベルとgoto文が数百個になると、ある行に「どこから来たのか」を知るために、プログラム全体を探さなければならなくなります。
処理の流れが絡み合った状態は、皿に盛ったスパゲッティにたとえて「スパゲッティコード」と呼ばれます。

1968年、ダイクストラはCommunications of the ACMに投書「Go To文は有害と考えられる（Go To Statement Considered Harmful）」を発表しました。
主張の中心は、プログラムの正しさを確かめるにはソースコードの字面と実行の進み方が対応していなければならず、goto文を自由に使うとその対応が崩れる、というものです。

### 構造化定理

これに先立つ1966年、ボーム（Corrado Böhm）とヤコピーニ（Giuseppe Jacopini）は、フローチャートで書けるどんな手順も、次の3つの構造の組み合わせだけで書き直せることを示しました。
これを構造化定理と呼びます。

| 構造 | 意味 | Javaの書き方 |
|------|------|--------------|
| 順次（sequence） | 上から順に実行する | 文を並べる |
| 分岐（selection） | 条件によってどちらか一方を実行する | `if`、`switch` |
| 反復（iteration） | 条件が成り立つあいだ繰り返す | `while`、`for` |

さきほどの関数は、3つの構造だけで次のように書けます。

```c
int find_structured(const int a[], int n, int key) {
    for (int i = 0; i < n; i++) {
        if (a[i] == key) {
            return i;
        }
    }
    return -1;
}
```

どちらの関数も、`{4, 8, 15}`から8を探すと1、9を探すと-1を返します（C言語のコンパイラーで確かめました）。

構造化プログラミングは、この定理とダイクストラの主張を土台に、「入口と出口が1つずつのかたまりを組み合わせてプログラムを作る」書き方として広まりました。
1972年には、ダール（Ole-Johan Dahl）、ダイクストラ、ホーア（C. A. R. Hoare）の3人による書籍『Structured Programming』が出版されています。
Javaにはgoto文がありません（`goto`は予約語ですが使えません）。
ラベル付きの`break`と`continue`はありますが、飛び先は、`break`ならラベルを付けて囲んでいる文（ループやブロック）の終わり、`continue`なら囲んでいるループの次の周回に限られます。
つまり、Javaは構造化プログラミングを言語の設計に取り込んでいます。

構造化定理の実装例は`src/main/java/com/example/theory/algorithms/StructuredProgramming.java`にあり、`java -ea -cp out com.example.theory.Main algorithms`で動かせます（ループ不変条件などは項目5の[05-algorithm-analysis.md](05-algorithm-analysis.md)と項目6の[06-formal-specification.md](06-formal-specification.md)で扱います）。

### 構造化の効果を数で見る：循環的複雑度

構造化しても、分岐が深く入れ子になると読みにくさは残ります。
読みにくさの目安として、判定（`if`や`case`など）の数に1を足した「循環的複雑度」が使われます（定義と数え方は項目3で詳しく説明します）。

`src/main/java/com/example/theory/complexity/ComplexityExample.java`には、同じ結果を返す2つの書き方があります。

- `processDataComplex`
    + `if`が3段の入れ子になっていて、循環的複雑度は5
- `processData`と`processType1`
    + 種類ごとの処理を別のメソッドに分け、どちらも循環的複雑度は3
    + 入れ子がなくなり、1つのメソッドで追う条件が減る

READMEの手順でコンパイルしてから、次のコマンドで実行します。

```bash
java -ea -cp out com.example.theory.Main complexity
```

見出しの後に、次の行が表示されます。

```
--- Cyclomatic Complexity Example ---
Complex method result: Type1-Long
Refactored method result: Type1-Long
```

2行が同じ結果になっていることから、書き直しても動作が変わっていないことを確かめられます。
複雑度の合計は5から6に増えていますが、1つのメソッドで同時に覚えておく条件は減っています。
構造化の目的は分岐の数を減らすことではなく、一度に理解しなければならない範囲を小さくすることだと、この例からわかります。

## 解決策2：モジュール化と情報隠蔽

### プログラムをどう分けるか

構造化プログラミングは、1つの関数のなかの流れを整理する考え方です。
プログラム全体が大きくなると、次に「プログラムをどんな部品（モジュール）に分けるか」が問題になります。

1972年、デイビッド・パーナス（David L. Parnas）は論文「システムをモジュールに分割する基準について（On the Criteria To Be Used in Decomposing Systems into Modules）」で、この問題に答えました。
パーナスは、文章から索引を作る小さなプログラム（KWIC索引）を例に、2つの分け方を比べました。

- 処理の手順で分ける方法
    + 「入力」「回転」「整列」「出力」のように、フローチャートの各段階をモジュールにする
    + データの持ち方（メモリ上の並べ方など）を、複数のモジュールが知っている
- 変わりそうな設計上の決定で分ける方法
    + データの持ち方のような「あとで変えたくなりそうな決定」を1つのモジュールのなかに閉じ込める
    + ほかのモジュールは、その決定を知らずに、決められた操作だけを使う

データの持ち方を変えると、前者では多くのモジュールを直す必要がありますが、後者では1つのモジュールを直すだけで済みます。
パーナスは後者を勧め、モジュールが隠すべきものを「そのモジュールの秘密」と呼びました。
この考え方を情報隠蔽（information hiding）と呼びます。

### C言語での情報隠蔽

C言語でも情報隠蔽はできます。
標準ライブラリの`FILE`型がその例です。
`fopen`が返す`FILE *`を受け取って`fgets`や`fclose`に渡しますが、利用者は`FILE`構造体の中身を知る必要がありません。
自分で作る場合は、ヘッダーファイルに構造体の名前だけを書き、中身はソースファイルのなかで定義します（項目2で例を示します）。

ただし、C言語には「この関数はこのファイルの外から呼べない」という指定（`static`）はあっても、構造体のメンバーごとに公開範囲を決める仕組みはありません。
Javaの`private`や`public`は、情報隠蔽を言語の機能として書けるようにしたものです（第3章「オブジェクト指向の考え方」、第4章「カプセル化とクラス設計」）。

## 解決策3：抽象データ型とオブジェクト指向

情報隠蔽をさらに進めたのが、データとその操作をひとまとまりの「型」として扱う考え方です。
1974年、バーバラ・リスコフ（Barbara Liskov）とスティーブン・ジルズ（Stephen Zilles）は、利用者からは操作だけが見える型を「抽象データ型（abstract data type、ADT）」として論文にまとめました。
リスコフはこの考え方をもとに、プログラミング言語CLUを設計しています。

オブジェクト指向は、これとは別の流れから生まれました。
1960年代にノルウェーのダール（Ole-Johan Dahl）とニゴール（Kristen Nygaard）がシミュレーションのために設計したSimula 67は、クラス、オブジェクト、継承を備えた最初の言語として知られています。
1970年代には、アラン・ケイ（Alan Kay）らがゼロックスのパロアルト研究所でSmalltalkを開発し、オブジェクトどうしがメッセージをやりとりして動くという見方を広めました。

抽象データ型の「データと操作をまとめて中身を隠す」考え方と、Simula以来のクラス・継承の仕組みが合わさったものが、Javaを含む今日のオブジェクト指向言語です。
詳しくは項目2で説明します。

## 解決策4：開発の進め方の改善

プログラムの書き方だけでなく、開発の進め方も見直されてきました。

- 段階的な開発
    + 要求の分析、設計、実装、テストを順に進める進め方は、ウォーターフォールモデルと呼ばれる
    + その説明によく引かれるRoyceの1970年の論文は、各段階を一度で終える進め方の危うさを指摘し、前の段階へ戻ることや試作を勧めている
- 反復型の開発
    + 小さく作って動かし、結果を見て直すことを繰り返す
    + 2001年に発表された「アジャイルソフトウェア開発宣言」は、この考え方を代表する文書である
- テストの自動化
    + プログラムを直すたびに、以前の動作が壊れていないかを機械で確かめる
    + 第21章「ユニットテストと品質保証」で扱う

## 銀の弾丸はない

1986年、ブルックスは論文「銀の弾丸はない（No Silver Bullet）」で、ソフトウェア開発の生産性を10年で10倍にするような単独の技術は現れないだろうと論じました。
論文の題名は、狼男を一撃で倒せる銀の弾丸という言い伝えにちなみます。

ブルックスは、ソフトウェアの難しさを2種類に分けました。

- 本質的な難しさ（essence）
    + 解こうとしている問題そのものが持つ複雑さ
    + 例: 業務の規則が多く例外だらけである、要求が途中で変わる
- 偶有的な難しさ（accident）
    + 問題を解くための道具や方法が持ち込む難しさ
    + 例: 機械語でしか書けない、コンパイルに時間がかかる

高水準言語や開発環境の進歩は、偶有的な難しさを大きく減らしてきました。
しかし本質的な難しさは道具では消えません。
ブルックスは本質的な難しさの性質として、複雑さ（complexity）、他のシステムや制度への適合（conformity）、変更され続けること（changeability）、目に見えないこと（invisibility）を挙げています。

この主張は、本書で学ぶ技術の位置づけを教えてくれます。
クラスやインターフェイスは本質的な複雑さを消すものではなく、複雑さを「分けて、隠して、1つずつ考えられるようにする」ための道具です。

## よくある誤解

- 「ソフトウェアクライシスは過去の話である」
    + 規模と複雑さが増えると同じ症状が起きるという構図は、今も変わらない。解決策が進んだぶん、作るものも大きくなっている
- 「構造化プログラミングとは、goto文を使わないことである」
    + goto文を使わないのは結果の1つにすぎない。目的は、コードの字面から実行の進み方を追えるようにして、正しさを確かめやすくすること
- 「オブジェクト指向にすれば、自然によい設計になる」
    + クラスを使っても、公開フィールドだらけで部品どうしが絡み合っていれば、手続き型の悪いプログラムと変わらない。何を隠し、何を公開するかを考えて初めて効果がある
- 「人を増やせば早く終わる」
    + ブルックスの法則のとおり、遅れてから人を増やすと連絡と教育の手間が増える。仕事を独立した部品に分けられるかどうかが鍵になる。これはモジュール化の問題でもある

## 実務での使いどころ

- 新しい技術や手法を学ぶときは、「それはどんな難しさを減らすためのものか」を考える。偶有的な難しさを減らすものか、本質的な複雑さを分割するものかで、期待できる効果が違う
- 部品の分け方に迷ったら、パーナスの基準を思い出す。「あとで変わりそうな決定」を1か所に閉じ込められる分け方を選ぶ
- 1つのメソッドが長く、入れ子が深くなったら、構造化の考え方に戻り、意味のあるかたまりごとにメソッドへ分ける
