# 3. ソフトウェア品質メトリクス：結合度、凝集度、循環的複雑度

## この項目で学ぶこと

「このクラスは設計がよい」「このメソッドは読みにくい」という判断は、人によってばらつきます。
ソフトウェア品質メトリクス（software quality metrics）は、こうした判断の手がかりを、できるだけ客観的な基準や数値で表そうとするものです。

この項目では、設計のよしあしを測る代表的な3つの尺度を説明します。

- 結合度（coupling）
    + モジュールどうしが、どれだけ強く依存し合っているか
- 凝集度（cohesion）
    + 1つのモジュールの中身が、どれだけ1つの目的にまとまっているか
- 循環的複雑度（cyclomatic complexity）
    + 1つのメソッドのなかに、処理の流れの分かれ道がいくつあるか

ここでいう「モジュール」は、プログラムを分けた部品のことです。
もとの理論ではC言語の関数のような手続きを指していましたが、Javaではメソッド、クラス、パッケージのどれにも当てはめて考えられます。

## なぜ測るのか

項目1で見たように、大きなプログラムの難しさの根は複雑さにあります。
ある部品を直すときに、ほかのどれだけの部品を調べ、直し、テストし直す必要があるか。
それを決めるのが部品どうしのつながり方（結合度）と、部品の中身のまとまり方（凝集度）です。

1974年、スティーブンス（W. P. Stevens）、マイヤーズ（G. J. Myers）、コンスタンティン（L. L. Constantine）は、IBM Systems Journalの論文「Structured Design」で、結合度と凝集度をモジュール設計の基準として示しました。
その後、ヨードン（Edward Yourdon）とコンスタンティンの書籍『Structured Design』（1979年）などで、結合度と凝集度をそれぞれ段階に分けた分類が広まりました。
目標は「結合度は低く、凝集度は高く」です。

- 結合度が低い
    + 1つの部品を変えても、ほかの部品に影響が広がりにくい
    + 部品を単独でテストしやすい
- 凝集度が高い
    + 部品の役割を一言で説明でき、変更の理由が1つに絞られる
    + どこを直せばよいかを見つけやすい

ISO/IEC 25010（ソフトウェア製品の品質モデルの国際規格）も、保守性の副特性としてモジュール性、再利用性、解析性、修正性、試験性を挙げています。
結合度と凝集度は、これらの性質を左右する設計上の要因です。

## 結合度

### 結合度の段階

結合度は、2つのモジュールのあいだで「何を通じて依存しているか」によって段階に分けられます。
次の表は、強い（悪い）ものから弱い（よい）ものの順に並べたものです。

| 段階 | 依存の仕方 | Javaでの例 |
|------|------------|------------|
| 内容結合（content） | 相手の内部（ローカルなデータや処理の途中）に直接触れる | リフレクションで他のクラスの`private`フィールドを書き換える |
| 共通結合（common） | 複数のモジュールが同じ大域的なデータを読み書きする | 書き換えられる`public static`フィールド、状態を持つSingleton |
| 外部結合（external） | 外部で決められたデータ形式・通信手順・装置を共有する | 2つのクラスが同じCSVの列の並びを前提に読み書きする |
| 制御結合（control） | 相手の処理の流れを決めるフラグを渡す | `process(data, mode)`の`mode`で処理を切り替える |
| スタンプ結合（stamp） | 構造を持つデータをまとめて渡し、相手はその一部だけを使う | 住所だけが要るメソッドに`Customer`オブジェクト全体を渡す |
| データ結合（data） | 必要な値だけを引数で渡し、戻り値で受け取る | `calculateTax(income, rate)` |

段階の名前や、外部結合をどこに置くかは、文献によって少し違います。
大切なのは、上へ行くほど、相手の内部の事情や、呼び出し側から見えないつながりに依存するという順序です。

### 実装例で確かめる

`src/main/java/com/example/theory/complexity/CouplingExamples.java`には、データ結合、スタンプ結合、制御結合、共通結合の例があります。
次のコマンドで、それぞれを動かすデモを実行できます。

```bash
java -cp out com.example.theory.complexity.CouplingExamples
```

```
--- Data coupling / Stamp coupling ---
calculateTax(50000, 0.2) = 10000.0
calculateTax(TaxInfo) = 10000.0
--- Control coupling ---
Processing mode 1: report
Processor A: report
Processor B: report
--- Common coupling ---
BadOrderProcessor failed: GlobalConfig has no database
Saved by test double: A-002
```

出力の読み方を順に説明します。

- データ結合とスタンプ結合
    + `calculateTax(double, double)`は、計算に必要な2つの値だけを受け取る（データ結合）
    + `calculateTax(TaxInfo)`は、値をまとめたオブジェクトを受け取る（スタンプ結合）
    + この例の`TaxInfo`は2つの値しか持たず、どちらも使うので問題は小さい。オブジェクトに無関係なフィールドが増えると、メソッドがその構造に依存し、テストのたびに不要なデータまで用意する必要が出てくる
- 制御結合
    + `processDataBad(data, mode)`は、呼び出し側が渡す数値で処理を選ぶ。呼び出し側は、相手のなかにどんな分岐があるかを知っていなければならない
    + 2回目の呼び出しでは`mode`に3を渡しているが、何も表示されない。想定外の値を渡した誤りに、誰も気づけない
    + `DataProcessor`インターフェイスと`ProcessorA`・`ProcessorB`の版では、処理の違いをクラスの違いで表すので、フラグを渡す必要がない。存在しない処理を選ぶこともできない
- 共通結合
    + `BadOrderProcessor`は、大域的な`GlobalConfig`から`Database`を取り出す。`GlobalConfig`に誰も`Database`を設定していなかったので、`NullPointerException`で失敗した
    + どの順番で誰が設定するかという、コードの字面に現れない約束に依存しているのが共通結合の問題である
    + `GoodOrderProcessor`は、コンストラクターの引数で`Database`を受け取る（依存性の注入）。デモでは、本物のデータベースの代わりに、保存したことを表示するだけのテスト用の偽物をラムダ式で渡している

共通結合を引数による受け渡しに変えると、依存が呼び出しの形に現れ、テストで差し替えられるようになります。
これは第21章「ユニットテストと品質保証」で学ぶテストの書きやすさに直結します。

### オブジェクト指向での結合度の測り方

クラス単位で結合度を数で表す尺度もあります。

- CBO（Coupling Between Object classes）
    + 1994年にChidamberとKemererが提案した、オブジェクト指向設計のための6つの尺度の1つ
    + あるクラスが、ほかのいくつのクラスと結合しているか（メソッドを呼ぶ、フィールドを使うなど）を数える
- 求心性結合（Ca）と遠心性結合（Ce）、不安定度（I）
    + ロバート・C・マーティン（Robert C. Martin）がパッケージの設計の尺度として紹介した
    + Caは、そのパッケージのなかのクラスに依存している、パッケージの外のクラスの数。Ceは、パッケージの外のクラスに依存している、そのパッケージのなかのクラスの数
    + 不安定度 I = Ce / (Ca + Ce) は0から1の値をとる。0に近いほど多くから頼られていて変えにくく（安定）、1に近いほど他に頼っていて変えやすい（不安定）

マーティンは、依存の向きを「不安定なものから安定したものへ」そろえることを勧めています。
多くの部品から頼られる部品（Iが小さい）が、頻繁に変わる部品に依存していると、その変更が広く波及するからです。

## 凝集度

### 凝集度の段階

凝集度は、1つのモジュールのなかの要素が「なぜ一緒にあるのか」によって段階に分けられます。
次の表は、強い（よい）ものから弱い（悪い）ものの順に並べたものです。

| 段階 | 要素が一緒にある理由 | 例 |
|------|----------------------|----|
| 機能的凝集（functional） | すべての要素が、1つのはっきりした機能に役立つ | 素数かどうかを判定する |
| 逐次的凝集（sequential） | ある要素の出力が、次の要素の入力になる | 整形→検証→変換の順に1つのデータを加工する |
| 通信的凝集（communicational） | 同じデータを入力または出力として使う | 1件の注文から、請求書と出荷指示を作る |
| 手続き的凝集（procedural） | 決まった順に実行されるが、データは受け渡さない | 権限を確かめてから、ログを開いて、画面を消す |
| 時間的凝集（temporal） | 同じ時期に実行される | 起動時の初期化処理をまとめたメソッド |
| 論理的凝集（logical） | 種類が似ているだけで、フラグで1つを選んで実行する | 出力先の種類を引数で受け取り、画面・CSV・HTMLのどれかに出力する |
| 偶発的凝集（coincidental） | 関係がない | 日付の整形、税金の計算、メール送信を集めた`Utilities` |

段階が下がるほど、「このモジュールは何をするものか」を一言で説明しにくくなります。
一言で説明するのに「と」や「または」が要るなら、凝集度が低い兆しです。

### 実装例で確かめる

`src/main/java/com/example/theory/complexity/CohesionExamples.java`には、機能的凝集、逐次的凝集、論理的凝集、偶発的凝集の例があります。

```bash
java -cp out com.example.theory.complexity.CohesionExamples
```

```
--- Functional cohesion ---
isPrime(17) = true, isPrime(20) = false
--- Sequential cohesion ---
process("  Hello Cohesion  ") = HELLO COHESION
--- Logical cohesion ---
[Sales]
<h1>Sales</h1>
```

- 機能的凝集の`PrimeChecker`
    + 「素数かどうかを判定する」という1つの機能だけを持つ。テストも「素数」「素数でない数」「2未満の数」を確かめれば済む
- 逐次的凝集の`DataProcessor`
    + `clean`（前後の空白を除いて小文字に）→`validate`（空でないか検査）→`transform`（大文字に）の順に、前の出力を次の入力にしている
    + 出力の`HELLO COHESION`は、前後の空白が取り除かれ、大文字になったことを示す
    + 段階ごとに別の型（`CleanedData`、`ValidatedData`）にしているので、検証していないデータを`transform`に渡すとコンパイルエラーになる
- 論理的凝集の`ReportOutput`
    + 「出力する」という種類が同じだけの3つの処理を、`kind`引数で選ばせている
    + 呼び出し側はフラグを渡すことになるので、制御結合も生む。結合度と凝集度は互いに関係している
    + 出力形式ごとのクラスに分け、共通のインターフェイスを実装させると、機能的凝集に近づく
- 偶発的凝集の`Utilities`
    + 日付の整形、税金の計算、メール送信、配列の整列という無関係な機能の寄せ集め。デモでは呼び出していない
    + このクラスはどの機能の変更でも書き換えられ、使う側は1つの機能のために全体に依存する

本文の第4章「クラスとインスタンス」で学ぶ単一責任の原則（クラスを変更する理由は1つにする）は、凝集度を高く保つための指針と言えます。

### 凝集度を数で表す

Chidamber と Kemerer の6つの尺度には、クラスの凝集度の低さを表すLCOM（Lack of Cohesion in Methods）もあります。
考え方は、「同じフィールドを使うメソッドの組が多いほど凝集度が高く、使うフィールドが重ならないメソッドの組が多いほど凝集度が低い」というものです。
たとえば、メソッドがAグループとBグループに分かれ、互いに同じフィールドを1つも使わないなら、そのクラスは2つのクラスに分けられる可能性があります。
LCOMには計算方法の異なる版がいくつかあり、ツールによって値の意味が違うので、比べるときは同じツールの値どうしで比べます。

## 循環的複雑度

### 定義

1976年、トーマス・マッケイブ（Thomas J. McCabe）は論文「A Complexity Measure」で、プログラムの制御の流れの複雑さを測る尺度として循環的複雑度を提案しました。
メソッドの処理の流れを、処理のかたまりを点（ノード）、流れを矢印（エッジ）とするグラフ（制御フローグラフ）で表したとき、循環的複雑度 V(G) は次の式で求めます。

```
V(G) = E − N + 2P

E: エッジの数
N: ノードの数
P: グラフの連結成分の数（1つのメソッドなら1）
```

例として、次のメソッドを考えます。

```java
static String classify(int n) {
    if (n < 0) {          // 判定1
        return "negative";
    } else if (n == 0) {  // 判定2
        return "zero";
    }
    return "positive";
}
```

このメソッドの制御フローグラフは次のようになります。

```
            [1] n < 0 ?
            /         \
         真            偽
          |             |
   [2] "negative"   [3] n == 0 ?
          |          /        \
          |        真          偽
          |         |           |
          |    [4] "zero"   [5] "positive"
          |         |           |
          +----> [6] 終了 <-----+
```

ノードは6つ、エッジは 1→2、1→3、3→4、3→5、2→6、4→6、5→6 の7本なので、V(G) = 7 − 6 + 2 = 3 です。

グラフを描かなくても、構造化されたプログラムなら、次の数え方で同じ値になります。

```
循環的複雑度 = 判定の数 + 1
```

判定として数えるのは、`if`、`else if`、`while`、`for`、`do-while`、`switch`の`case`、三項演算子`?:`、`catch`、そして条件式のなかの`&&`と`||`です。
`else`と`default`は新しい判定ではないので数えません。
`classify`の判定は2つなので、2 + 1 = 3 です。
`&&`と`||`を数えるのは、短絡評価によって右側を評価するかどうかが分かれるからです。
たとえば `return (day == 6 || day == 7) && member;` は`if`を含みませんが、`||`と`&&`で判定が2つあり、循環的複雑度は3です。
数え方の細部（`case`や`catch`、`&&`の扱い）はツールによって少し違います。

### 循環的複雑度が表すもの

循環的複雑度は、メソッドの入口から出口までの「独立な経路」の数に当たります。
独立な経路とは、ほかの経路の組み合わせでは表せない経路のことです。
`classify`なら、負の数・0・正の数を渡す3つの入力で、3本の経路をすべて通れます。

このことから、循環的複雑度はテストの量の目安にもなります。

- すべての分岐の真と偽を1回ずつ通す（分岐網羅）のに必要なテストの数は、循環的複雑度の値を超えない
- 独立な経路を1本ずつ通すテスト（基底経路テスト）を作るなら、テストの数は循環的複雑度と同じになる

マッケイブは論文のなかで、1つのモジュールの循環的複雑度の上限の目安として10を挙げています。
ただし、これは絶対の基準ではなく、上限を超えたモジュールを見直すきっかけとして使うものです。

### 実装例で確かめる

`src/main/java/com/example/theory/complexity/ComplexityExample.java`には、同じ結果を返す2つの書き方があります。
各行のコメント`// +1`が、判定として数えた箇所です。

| メソッド | 判定 | 循環的複雑度 |
|----------|------|--------------|
| `processDataComplex` | `if`が3つ、`else if`が1つ | 5 |
| `processData` | `case`が2つ（`default`は数えない） | 3 |
| `processType1` | `if`が1つ、三項演算子が1つ | 3 |

`java -ea -cp out com.example.theory.Main complexity`を実行すると、見出しの後に次の行が表示されます。

```
--- Cyclomatic Complexity Example ---
Complex method result: Type1-Long
Refactored method result: Type1-Long
```

2つのメソッドに同じ引数（種類1、フラグtrue、11文字の文字列）を渡して、同じ結果になることを確かめています。
書き直した後の合計（3 + 3 = 6）は、書き直す前（5）より大きくなっています。
それでも、1つのメソッドで追う判定は4つから2つに減り、入れ子もなくなりました。
循環的複雑度はメソッドごとに測るもので、「1つのメソッドを理解するために、同時に考える分かれ道の数」を表しています。

## よくある誤解と注意点

- 「数値がよければ、よい設計である」
    + メトリクスは設計の一面だけを測る。循環的複雑度を下げるためだけにメソッドを細かく分けすぎると、処理を追うためにメソッドをいくつも行き来することになり、かえって読みにくくなる
- 「メトリクスの目標値を決めて、達成を評価する」
    + 数値そのものを目標にすると、数値をよく見せるための変更（意味のない分割、判定を別の書き方に隠すなど）が起きやすい。数値は「どこから見直すか」を決める手がかりとして使う
- 「結合度はゼロにするべきである」
    + 部品どうしがまったく結合していなければ、協力して働けない。目標は結合をなくすことではなく、必要な結合を弱い形（データ結合やインターフェイスを通した依存）にすること
- 「凝集度の段階は、きっちり1つに決まる」
    + 実際のモジュールは複数の段階の性質を持つことが多い。分類は、まとめ方の理由を考えるための道具として使う
- 「行数が少なければ単純である」
    + 1行に`&&`と`||`と三項演算子を詰め込んだ式は、行数が少なくても循環的複雑度は高い

## 実務での使いどころ

- 静的解析ツール（PMD、Checkstyle、SonarQubeなど）は、循環的複雑度や結合の数をメソッド・クラスごとに報告できる。上限を超えたものを一覧にして、見直す順番を決めるのに使う
- コードレビューでは、「このクラスの役割を一言で言えるか」（凝集度）、「このメソッドは引数に何を求めているか、大域的な状態に頼っていないか」（結合度）を確かめる
- テストが書きにくいクラスは、結合度が高いことが多い。テストのために大域的な状態を用意する必要があるなら、依存を引数で受け取る形に変える
- 複雑度の高いメソッドを直すときは、先にテストを書いて動作を固定してから分割する（第21章「ユニットテストと品質保証」）
