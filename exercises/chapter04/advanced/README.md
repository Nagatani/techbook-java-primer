# 第4章 発展課題

## 学習目標
- フィールドを`private`にし、検証してから値を変える`public`メソッドだけを入り口にする
- 見せたくない値（パスワードなど）にはgetterを作らず、「合っているかどうか」だけを答える
- パッケージプライベート（修飾子なし）で、同じパッケージのクラスにだけ操作を許す
- `this(...)`で標準の値を補うコンストラクターと、引数の型が違うメソッドのオーバーロードを書く
- 値を変えてはいけないフィールドに`final`を付ける

## 課題一覧

### 課題1: ログインの管理（アカウントのロック）
**ファイル**（このフォルダーのファイルは解答例です）:
```
advanced/task1-login/
├── login/
│   ├── UserAccount.java   利用者のアカウント
│   └── LoginService.java  登録・ログイン・ロックの解除を受け付ける
└── app/
    └── LoginApp.java      mainメソッド
```

パスワードを3回続けてまちがえるとロックされるログインの仕組みを作成してください。
アカウントのクラスは`login`パッケージに、`main`メソッドは`app`パッケージに置きます。

**要求仕様**:
- `UserAccount`（アカウント）
    - 利用者ID・権限（「一般」か「管理者」）・パスワードのハッシュ値・続けて失敗した回数・ロック中かどうかを持つ。すべて`private`にする
    - パスワードはそのまま保存せず、変換した値（ハッシュ値）だけを持つ。パスワードやハッシュ値を返すgetterは作らない
    - 権限を省いたコンストラクターは、`this(...)`で「一般」を指定してもう1つのコンストラクターを呼ぶ
    - IDが空、パスワードが8文字未満、権限が2つのどちらでもないときは`IllegalArgumentException`を投げる
    - `login(パスワード)`は、正しければ失敗の回数を0に戻して`true`を返す。まちがえると回数を1増やし、3回でロックする。ロック中は正しいパスワードでも`false`
    - `changePassword(いまのパスワード, 新しいパスワード)`は、いまのパスワードが正しく、新しいパスワードが8文字以上のときだけ変更する
    - ロックの解除`unlock()`はパッケージプライベートにして、`app`パッケージからは呼べないようにする
- `LoginService`
    - アカウントを配列で管理する。同じIDは登録しない
    - ログインの結果（成功・失敗の回数・ロック・未登録）を表示する
    - 管理者のIDとパスワードが正しいときだけ、ほかの利用者のロックを解除する
    - 登録数・ロック中の人数・パスワードをまちがえた回数を表示する

**実行例**:
```
=== 登録 ===
登録しました: admin（管理者）
登録しました: tanaka（一般）
登録できません: tanaka

=== ログイン ===
tanaka: ログインしました（一般）
tanaka: パスワードが違います（1/3回）
tanaka: パスワードが違います（2/3回）
tanaka: パスワードが違います（3/3回）。ロックしました
tanaka: ロック中のためログインできません
suzuki: 登録されていません

=== ロックの解除 ===
tanakaのロック解除: 管理者として確認できません
tanakaのロック解除: 解除しました
tanaka: ログインしました（一般）

=== パスワードの変更 ===
登録しました: sato（一般）
短すぎる新しいパスワード: 変更できません
正しい手順: 変更しました
sato: ログインしました（一般）

=== 状況 ===
登録数: 3人、ロック中: 0人、パスワードの誤り: 3回
```

1回目のロック解除は、一般の利用者（tanaka）が自分で解除しようとしたので断られます。

### 課題2: アプリの設定の管理
**ファイル**（このフォルダーのファイルは解答例です）:
```
advanced/task2-settings/
├── AppSettings.java  設定（ポート番号・最大利用者数・ログの詳しさ）
└── SettingsApp.java  mainメソッド
```

開発用と本番用で標準の値が違うアプリの設定を、正しい値にしか変えられないクラスとして作成してください。

**要求仕様**:
- 環境（「開発」か「本番」）・データベースのパスワード・ポート番号・最大利用者数・ログの詳しさ（`DEBUG`・`INFO`・`WARN`・`ERROR`のどれか）を`private`のフィールドで持つ
- 環境とデータベースのパスワードは、あとから変えないので`final`にする
- すべての値を指定するコンストラクターで値を検証する。環境とパスワードだけを指定するコンストラクターは、環境ごとの標準の値（開発: 8080・100人・`DEBUG`、本番: 80・10000人・`INFO`）で、`this(...)`を使ってもう1つのコンストラクターを呼ぶ
- 値を変えるメソッドは`set(名前, int値)`と`set(名前, String値)`のオーバーロードにする。ポート番号は1〜65535、最大利用者数は1以上、ログの詳しさは4つのどれかのときだけ変えて`true`を返す。名前が違うときや範囲の外のときは変えずに`false`を返す
- 変えた内容を「名前: 前の値 → 新しい値」の形で、配列に履歴として残す。履歴は表示するメソッドだけを用意し、配列は外へ渡さない
- データベースのパスワードのgetterは作らず、`matchesDbPassword(パスワード)`で合っているかどうかだけを返す。設定の表示ではパスワードを`****`にする

**実行例**:
```
=== 標準の値 ===
[開発] port=8080, maxUsers=100, logLevel=DEBUG, dbPassword=****
[本番] port=80, maxUsers=10000, logLevel=INFO, dbPassword=****

=== 開発環境の設定を変える ===
port → 9090: 変更しました
maxUsers → -1: 変更できません
logLevel → VERBOSE: 変更できません
logLevel → WARN: 変更しました
timeout → 30: 変更できません
[開発] port=9090, maxUsers=100, logLevel=WARN, dbPassword=****

=== 変更の履歴 ===
開発:
  1. port: 8080 → 9090
  2. logLevel: DEBUG → WARN
本番:
  変更はありません

=== パスワードの確認 ===
dev-secretか: true
prod-secretか: false
```

### 課題3: 口座のあいだの振込
**ファイル**（このフォルダーのファイルは解答例です）:
```
advanced/task3-bank/
├── bank/
│   ├── Account.java      口座
│   ├── Transaction.java  1件の振込（作ったあとは変えられない）
│   └── Bank.java         口座の開設と振込を行う
└── app/
    └── BankApp.java      mainメソッド
```

口座から口座へお金を振り込むプログラムを作成してください。
振込のたびに手数料200円を、振り込む側の口座から引きます。

**要求仕様**:
- `Account`（口座）
    - 口座番号・名義・開設時の残高を`final`で、残高と取引の履歴を`private`で持つ
    - コンストラクターと、残高を変えるメソッド（引き出す・預ける）、履歴を加えるメソッドはパッケージプライベートにする。`app`パッケージからは残高を読めるが、変えられない
    - 履歴は加えるだけで、消したり書き換えたりするメソッドを作らない
- `Transaction`（振込）
    - 取引番号（`T001`からの連番）・振り込む口座・受け取る口座・金額・手数料を持つ。フィールドはすべて`final`で、setterを作らない
    - コンストラクターはパッケージプライベートにし、`Bank`だけが作れるようにする
- `Bank`（銀行）
    - 口座を配列で管理する。`open(番号, 名義, 最初の入金額)`と、入金額を省いた`open(番号, 名義)`を用意する。同じ番号の口座は開かない
    - 振込は、口座番号で指定する`transfer(String, String, int)`と、口座のオブジェクトで指定する`transfer(Account, Account, int)`のオーバーロードにする。口座番号の版は口座を探して、もう一方に処理を任せる
    - 口座がない・同じ口座・金額が0以下・残高が「金額 + 手数料」に足りないときは、どちらの残高も変えずに理由を表示し`false`を返す。条件をすべて確かめてから、2つの口座の残高をまとめて変える
    - 監査として、成功と失敗の件数と、「開設時の残高の合計 = いまの残高の合計 + 受け取った手数料」が成り立つかを表示する

**実行例**:
```
=== 口座の開設 ===
口座を開きました: A001（山田太郎） 100000円
口座を開きました: A002（佐藤花子） 50000円
口座を開きました: A003（鈴木一郎） 0円
口座を開けません: A001

=== 振込 ===
振込 A001 → A002 30000円
  T001 完了（手数料200円） 残高 山田太郎様 69800円 / 佐藤花子様 80000円
振込 A002 → A001 100000円
  できません: 残高が足りません（必要 100200円、残高 80000円）
振込 A002 → A003 79800円
  T002 完了（手数料200円） 残高 佐藤花子様 0円 / 鈴木一郎様 79800円
振込 A003 → （不明） 500円
  できません: 口座が見つかりません
振込 A001 → A001 1000円
  できません: 同じ口座には振り込めません

=== 取引の履歴 ===
A001（山田太郎）の取引:
  開設          +100000円
  T001 振込送金 -30200円（佐藤花子様へ、手数料200円を含む）
  残高 69800円
A002（佐藤花子）の取引:
  開設          +50000円
  T001 振込受取 +30000円（山田太郎様から）
  T002 振込送金 -80000円（鈴木一郎様へ、手数料200円を含む）
  残高 0円

=== 監査 ===
みどり銀行の監査:
  振込 成功 2件、失敗 3件
  開設時の残高の合計 150000円 = いまの残高の合計 149600円 + 手数料 400円: 一致
```

## 実装のヒント

```java
public class UserAccount {
    private int passwordHash;   // パスワードそのものは持たない

    // 権限を省いたときは、もう1つのコンストラクターに「一般」を渡す
    public UserAccount(String userId, String password) {
        this(userId, password, ROLE_USER);
    }

    // 修飾子を付けないと、同じパッケージ（login）からだけ呼べる
    void unlock() {
        locked = false;
        failureCount = 0;
    }
}
```

- 課題1のハッシュ値は、練習のため`String`の`hashCode()`で作ってよい。実際のシステムでは、パスワード専用のハッシュ関数を使う
- `app`パッケージで`account.unlock()`や`new Transaction(...)`と書いて、コンパイルエラーになることを確かめる
- 課題2の`set("port", 9090)`は`int`版、`set("logLevel", "WARN")`は`String`版が呼ばれる。どちらが呼ばれるかは引数の型でコンパイル時に決まる
- 課題3で「引いてから足りないことに気づく」順にすると、片方の口座だけが変わった状態が残る。振込の前に、理由を返す`check`メソッドで条件をまとめて確かめる
- 不正な値で投げた例外を受け止める方法（`try`〜`catch`）は第13章で学ぶ。ここでは、正しい値で呼び出すプログラムを書く。パスワードのまちがいや残高不足など、ふつうに起きる失敗は例外ではなく`false`や`null`で知らせる
- 配列を`return`で外へ渡すと、受け取った側が中身を書き換えられる。これを防ぐ方法（防御的コピー）は第6章で学ぶので、ここでは履歴を表示するメソッドだけを用意する

## 応用のポイント

1. 入り口を決める
    - 値を変える方法を検証つきのメソッドだけにすると、範囲の外の値を持つオブジェクトは作れなくなる
2. 見せる範囲を決める
    - パスワードのように外へ出さない値は、getterを作らずに「合っているか」を答えるメソッドにする
3. パッケージで仲間を決める
    - 残高を変える操作を`bank`パッケージの中に閉じ込めると、手数料や履歴を残さずに残高を変える処理は書けなくなる

## 発展（任意）

- 課題1で、ロックしてから決まった回数のログインの試みがあれば、自動で解除されるようにする
- 課題2に、設定を変える前の値に1つ戻す`undo()`を加える。履歴にどんな情報を残せばよいかを考える
- 課題3に、1日に振り込める金額の上限を加える。どのクラスに書くのがよいかを考える

## 完了チェックリスト

- [ ] パスワードやハッシュ値を返すメソッドがない

- [ ] 標準の値を補うコンストラクターが`this(...)`を使っている
