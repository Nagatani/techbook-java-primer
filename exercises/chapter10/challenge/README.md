# 第10章 チャレンジ課題

## 学習目標
- 型パラメーターを持つインターフェイスを定義し、クラスやレコードで実装する
- 複数の型パラメーターに境界を付けたジェネリッククラスを設計する
- 上限境界ワイルドカード（`? extends`）・下限境界ワイルドカード（`? super`）・非境界ワイルドカード（`?`）を使い分ける
- 番号の型が違うデータを、同じジェネリッククラスで型安全に管理する
- 右辺から型がわかる場面で`var`を使う

## 課題一覧

### 課題1: サークルの備品貸出管理
**ファイル**（このフォルダーのファイルは解答例です）:
```
challenge/
├── Identifiable.java  番号を持つもの（ジェネリックインターフェイス）
├── Repository.java    番号でデータを登録・検索する入れ物
├── Member.java        会員（レコード）
├── Equipment.java     備品
├── LendingDesk.java   貸出窓口
├── Report.java        一覧の表示
└── LendingApp.java    mainメソッド
```

サークルのカメラや三脚などの備品を会員に貸し出すプログラムを作成してください。
会員の番号は`"S001"`のような文字列、備品の番号は`101`のような整数です。
番号の型が違う会員と備品を、同じジェネリッククラス`Repository`で管理します。

**要求仕様**:
- `Identifiable<K>`
    - 番号を返す`K getId()`だけを持つインターフェイス
- `Repository<K extends Comparable<K>, V extends Identifiable<K>>`
    - データを番号の順に並ぶ`TreeMap<K, V>`で持つ
    - 登録（同じ番号があれば`false`）、番号で探す（なければ`null`）、削除、すべてのデータ、件数
    - 番号が範囲に入るデータを返す`findRange(K from, K to)`
    - `addAll(Collection<? extends V>)`でまとめて登録し、登録できた数を返す
    - `exportTo(Collection<? super V>)`で、すべてのデータを渡されたコレクションに加える
- `Member`（会員）
    - 番号と名前を持つレコード。`Identifiable<String>`を実装する
- `Equipment`（備品）
    - 番号・名前・借りている会員の番号・返却期限の日を持つクラス。`Identifiable<Integer>`を実装する
    - 100番台がカメラ、200番台が三脚、300番台がプロジェクター
- `LendingDesk`（貸出窓口）
    - `Repository<String, Member>`と`Repository<Integer, Equipment>`を持つ
    - 貸出期間は7日。1人が同時に借りられるのは2点まで
    - 会員がいない・備品がない・貸出中・借りている数が上限のときは貸し出さず、理由を返す
    - 返却（期限より遅れたら遅れた日数を添える）、会員が借りている備品、期限を過ぎた備品
- `Report`
    - `printAll(String, Collection<? extends Identifiable<?>>)`で、会員でも備品でも一覧を表示する
- 会員と備品を`exportTo`で1つの`List<Identifiable<?>>`にまとめ、一覧を表示する

**実行例**:

## 実装のヒント

```java
// 型パラメーターを持つインターフェイス
public interface Identifiable<K> {
    K getId();
}

// 実装するときに、Kに当たる型を決める
public record Member(String id, String name) implements Identifiable<String> {
    @Override
    public String getId() {
        return id;
    }
}

// TreeMapのsubMapで、番号の範囲を取り出す
public List<V> findRange(K from, K to) {
    return new ArrayList<>(items.subMap(from, true, to, true).values());
}
```

- インターフェイスにも、クラスと同じように型パラメーターを付けられる。標準ライブラリの`Comparable<T>`や`List<E>`も同じ形である
- `K extends Comparable<K>`の境界は、`TreeMap`が番号を比べて並べるために付ける。`String`と`Integer`はどちらも`Comparable`を実装している
- `V extends Identifiable<K>`の境界があるので、`Repository`の中で`item.getId()`を呼べ、その戻り値は`K`型になる
- `Repository<Integer, Member>`のように番号の型が合わない組み合わせは、コンパイルエラーになる
- `Identifiable<?>`は「何かの型の番号を持つもの」を表す。番号の型が違う会員と備品を、1つのリストに入れられる
- `Equipment`の番号は`int`のフィールドに持ち、`getId()`で`Integer`として返す（オートボクシング）
- 見つからないときに`null`を返す代わりの`Optional`は第12章で学ぶ

## 応用のポイント

1. 型パラメーターの境界で「何ができるか」を約束する
    - `Repository`は会員や備品のことを知らないが、境界のおかげで「番号を取り出す」「番号を比べる」ことができる
2. ワイルドカードの使い分け
    - 取り出して使う引数（`addAll`、`printAll`）は`? extends`、入れる先の引数（`exportTo`）は`? super`、型を問わず読むだけなら`?`
3. 型の誤りはコンパイル時に見つかる
    - 会員の入れ物に備品を登録する、番号に違う型を渡す、といった誤りがキャストなしで防げる
