# 第26章 チャレンジ課題 - 解答の方針

この課題にはコードの解答例を用意していません。
ここでは、フェーズ6の構成を保ったまま機能を加える場合の方針と、変更するファイルを示します。

## 先に決めること

1. 保存の方式
    + フェーズ6と同じく「メモリを変えてからデータベースを変え、失敗したらメモリを戻す」形で書くか、データベースだけを保存先にする改善版の形に移してから加えるか
    + この課題の範囲だけなら前者が小さく済む。ただし、元に戻す処理がまた1つ増える。どちらを選んだかと理由を、設計判断記録に書く
2. 値の検査をどこで行うか
    + フェーズ6の`Person.setAge`は、0以下の値を黙って無視する。このままでは、誤った年齢を入力しても利用者に伝わらない
    + 検査はサービスか学生のクラスで行い、誤りは例外で画面に伝える（第25章の「誤りの種類を分ける」）

## 変更するファイルと順序

各手順の終わりで、`Phase6Test`を実行し、画面を少し操作して確かめます。

1. `StudentService`に`updateStudent(String studentId, String name, int age, String department)`を加える
    + 入力を検査し、誤りなら`IllegalArgumentException`などで理由を伝える
    + 変更前の値を覚えておき、`dbManager.saveStudent`が失敗したらメモリ上の値を元に戻して`IllegalStateException`を投げる（`updateGrade`と同じ形）
2. 確認のプログラムに、変更の確認を加える
    + 変更した値を、データベースから読み直しても同じになることを確かめる。メモリ上のデータベース（`jdbc:sqlite::memory:`）を使えば、ファイルを汚さない
3. 画面に「編集」のボタンとダイアログを加える
    + 学生の追加のダイアログ（`showAddStudentDialog`）を参考に、選んだ学生の値を入れた状態でダイアログを開く。学生IDの欄は編集できないようにする
    + 一覧の行をダブルクリックすると成績管理が開くので、編集はボタンかメニューから開くようにする
4. 学部の一覧を更新する
    + 学部を変えたら、絞り込みの学部の一覧（`JComboBox`）も作り直す

## 振り返りの例

この機能を加えると、サービス・画面・確認のプログラムの3つのファイルを直すことになります。
`DatabaseManager`は、`saveStudent`がUPSERTで既存の行を更新するので、変えずに済みます。
変えにくかった点として、`setAge`が誤りを黙って無視することと、元に戻す処理を手で書く必要があることが挙げられます。
これらは、第25章の改善版（値の検査をコンストラクターに集め、データベースだけを保存先にする）で解消できます。
