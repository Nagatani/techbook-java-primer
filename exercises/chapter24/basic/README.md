# 第24章 基礎課題 - 統合プロジェクトの設計

## 課題概要

第24章で学んだ要求の整理と設計判断記録を、別の題材で練習します。
あわせて、改善版の学生管理システムに小さな機能を加え、「計算で求められる値」と「記録すべき事実」の違いを確かめます。

このフォルダーには解答例を置いていません。解答例は[solutions/](../solutions/)にあります。

## 課題1: 図書の貸し出しを管理するシステムの設計

大学の研究室にある本（数百冊）を、研究室の学生が借りたり返したりするのを記録するシステムを考えます。
次の4つを、Markdownの文書（`library-design.md`）に書いてください。

**要件:**

1. ユーザーストーリーを5つ以上
    + 「〈役割〉として、〈目的〉のために、〈機能〉がほしい」の形で書く。役割は研究室の学生と、本を管理する担当者の2つ以上にする
2. 非機能要求を4つ
    + 扱う量・利用者・環境・配布について、数字を入れて書く
3. 作らないものを3つ以上
    + 「この版では作らない」機能と、作らない理由
4. 設計判断記録を1つ
    + 第24章の5つの項目（状況・選択肢・決定・理由・影響）で書く
    + 題材は「本が貸し出し中かどうかを、本のフィールド（`boolean onLoan`）で持つか、貸し出しの記録から求めるか」とする

**ヒント:**

- 「目的」を書くと、設計に効く条件が見つかる。たとえば「延滞している人に連絡するために」と書けば、返却の期限が必要だとわかる
- 設計判断記録の「影響」には、選んだ案によって変わる画面やデータを書く

## 課題2: 成績の訂正の履歴を残す

改善版の学生管理システムでは、同じ科目の成績を記録し直すと、前の成績は消えます。
採点の誤りを訂正したときに、訂正前と訂正後の成績を履歴として残せるようにしてください。

サンプルコード24-2の全文（`sample-code/chapter24/24-02/`）をコピーして始めます。

**要件:**

- 訂正の記録を表すRecord`GradeChange`（科目名・訂正前の`Grade`・訂正後の`Grade`）を作る
- `Transcript`の`record`で、同じ科目の成績を別の値に置き換えたときだけ、`GradeChange`を履歴に加える。同じ値を記録し直したときは加えない
- `Transcript`に履歴を返す`history()`、`Student`に`getGradeHistory()`を加える。返すリストは変更できないものにする
- GPAは、これまでどおり最新の成績から計算する
- 動作を確かめるプログラム`GradeHistoryCheck`を作る

**実行例:**

```
訂正前のGPA: 2.67
訂正後のGPA: 3.33
線形代数: 2.0 → 3.0
すべての確認に成功しました
```

**考えてみよう:**

GPAは保存せずに計算しますが、訂正の履歴は保存します。
第24章の事例3を読み返し、この2つの扱いが違う理由を説明してください。
