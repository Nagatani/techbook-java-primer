# 第22章 チャレンジ課題（APIドキュメントとライブラリ設計）

## 学習目標
- 使う人の立場で、小さなライブラリの公開API（クラス・メソッド・例外）を設計する
- 公開するものと内部に隠すものを、アクセス修飾子とパッケージで分ける
- 不変のレコード、変更できないリスト、`Optional`、例外を使い分け、それぞれの約束をJavadocに書く
- パッケージの説明（`package-info.java`）に、ライブラリ全体の使い方と約束をまとめる
- 自分で作ったライブラリを、別のプログラムからクラスパスで使う

## 課題一覧

### 課題1: ToDoリストのライブラリ
**ファイル**（このフォルダーのファイルは解答例です）:
```
challenge/
└── src/
    ├── todo/
    │   ├── package-info.java           ライブラリ全体の説明と約束
    │   ├── TodoList.java               タスクの一覧（ライブラリの中心のクラス）
    │   ├── Task.java                   1つのタスク（レコード）
    │   ├── Priority.java               優先度（enum）
    │   └── TaskNotFoundException.java  タスクがないときの例外
    └── demo/
        └── TodoApp.java                ライブラリを使う側のmainメソッド
```

ToDoリスト（やることの一覧）を管理するライブラリ`todo`を設計し、Javadocを付けてください。
作ったライブラリは、別のパッケージ`demo`のプログラムから、公開したAPIだけを使って利用します。

**要求仕様**:
- `TodoList`（タスクの一覧）
    - `add(名前, 優先度, 期限)`でタスクを登録し、1から順に番号を割り当てたタスクを返す。削除した番号は再利用しない
    - `find(番号)`は`Optional<Task>`を返す。`complete(番号)`（完了にする）と`remove(番号)`（削除する）は、番号がなければ`TaskNotFoundException`を投げる
    - `all()`（すべて）、`pending()`（未完了）、`overdue(今日)`（期限を過ぎた未完了）、`sortedByDue()`（未完了を期限の早い順。同じ期限は優先度の高い順、それも同じなら番号の順）を持つ
    - 一覧を返すメソッドは、すべて変更できないリストを返す
    - 今日の日付はライブラリの中で`LocalDate.now()`を呼ばず、引数で受け取る
- `Task`（1つのタスク）
    - 番号・名前・優先度・期限・完了したかを持つ、不変のレコード
    - 名前・優先度・期限が`null`なら`NullPointerException`、名前が空白だけなら`IllegalArgumentException`を投げる
    - `isOverdue(今日)`で、期限を過ぎていて未完了かを返す（期限の当日は過ぎていない）
    - 完了にしたタスクを作るメソッドはパッケージの外に公開せず、完了にする操作は`TodoList`を通してだけ行えるようにする
- `Priority`（優先度）は`HIGH`・`MEDIUM`・`LOW`のenumで、表示用の「高」「中」「低」を返す
- `TaskNotFoundException`は非チェック例外とし、見つからなかった番号を返すメソッドを持つ
- Javadoc
    - `package-info.java`に、ライブラリの概要、使用例、ライブラリ全体に共通する約束（`null`の扱い、変更できないリスト、日付を引数で受け取ること）を書く
    - 公開するすべての型・コンストラクター・メソッド・enumの定数に説明を書く
    - `find`と`complete`のように、「ないとき」の扱いが違うメソッドは、その違いがわかるように書く
    - 非チェック例外にした理由を、例外クラスの説明に書く
    - `javadoc -Xdoclint:all`で、警告もエラーも出ない

**実行例**（`TodoApp`の実行結果）:
```
=== すべてのタスク ===
  1 [中] 図書館に本を返す（期限 2026-06-02）
  2 [高] 情報数学のレポート（期限 2026-06-05）
  3 [低] サークルの会計報告（期限 2026-06-05）
  4 [低] 歯医者の予約（期限 2026-05-30）
  5 [高] プログラミング演習の課題（期限 2026-06-03）
削除: 歯医者の予約
=== 期限の早い順（未完了） ===
  5 [高] プログラミング演習の課題（期限 2026-06-03）
  2 [高] 情報数学のレポート（期限 2026-06-05）
  3 [低] サークルの会計報告（期限 2026-06-05）
=== 2026-06-04の時点で期限を過ぎたタスク ===
  5 [高] プログラミング演習の課題（期限 2026-06-03）
完了にできません: 番号4のタスクはありません
番号9のタスク: なし
```

1番のタスクを完了にし、4番のタスクを削除したあとの一覧です。
期限が同じ6月5日の2つは、優先度の高い順に並んでいます。

## コンパイルと実行

ライブラリと、それを使うプログラムを別々にコンパイルします。
ライブラリのクラスファイルを`lib`に出力し、`demo`をコンパイル・実行するときに`-cp lib`でクラスパスに加えます。
第22章で学んだ外部ライブラリの使い方と同じ形です。

```bash
# ライブラリをコンパイルする
javac -d lib src/todo/*.java

# ライブラリをクラスパスに加えて、使う側をコンパイル・実行する
javac -cp lib -d app src/demo/TodoApp.java
java -cp lib:app demo.TodoApp

# APIドキュメントを生成する
javadoc -Xdoclint:all -d doc -encoding UTF-8 -docencoding UTF-8 -charset UTF-8 -sourcepath src todo
```

Windowsでは、`-cp lib:app`の区切りを`;`にして`-cp "lib;app"`と書きます。
`doc/index.html`をブラウザーで開くと、パッケージの説明とクラスの一覧が表示されます。

## 実装のヒント

```java
// 一覧は、中身をコピーした変更できないリストで返す
public List<Task> all() {
    return List.copyOf(tasks);
}

// 「ないかもしれない」ことが普通の操作はOptional、「あるはず」の操作は例外
public Optional<Task> find(int id) { ... }
public Task complete(int id) { ... }   // なければTaskNotFoundException

// パッケージの外に見せないメソッドは、修飾子を付けない（パッケージプライベート）
Task completed() {
    return new Task(id, title, priority, due, true);
}
```

- 内部の`ArrayList`をそのまま返すと、使う側が`clear()`などで中身を書き換えられてしまう。`List.copyOf`でコピーを返す
- `Task`をレコードにすると、使う側はタスクを変更できない。完了にした新しい`Task`を作り、`TodoList`の中のリストで置き換える
- レコードのコンパクトコンストラクター（`public Task { ... }`）で引数を検査すると、不正なタスクが作られることがない
- `sortedByDue`は`Comparator.comparing(Task::due).thenComparing(Task::priority).thenComparingInt(Task::id)`で並べる。enumは宣言した順に比べられる
- 使う側のプログラムを別のパッケージに置くと、パッケージプライベートのメソッドを呼べないことで、公開の範囲が正しいかを確かめられる
- ドキュメントに書きにくいメソッドは、設計を見直す合図になる。たとえば「完了済みのタスクを`complete`したら」を書こうとすると、その動きを決める必要に気付く

## 応用のポイント

1. 公開するものを最小にする
    - 公開したメソッドは、利用者が使い始めると変えられなくなる。迷ったら公開しない（後から公開するのは簡単だが、公開をやめるのは難しい）
2. 約束をパッケージの説明にまとめる
    - `null`の扱いや戻り値のリストの性質を、メソッドごとではなく、ライブラリ全体の約束として1か所に書くと、利用者が覚えやすい
3. テストしやすいAPI
    - 今日の日付を引数で受け取るので、`overdue`の結果が実行する日に左右されない。第21章で学んだテストも書きやすい
